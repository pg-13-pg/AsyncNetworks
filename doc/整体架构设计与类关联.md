# UCP 整体架构设计与类关联

本文以当前仓库源码为准，说明 UCP（uring_coroutine_proactor）的分层结构、主要类之间的关联、连接生命周期、线程归属、协程 I/O 链路以及组件之间的解耦方式。

## 1. 项目定位

UCP 是一个 Linux TCP 网络框架，底层使用 io_uring，上层使用 C++20 协程，整体采用 Proactor 风格：

~~~text
应用提交异步 I/O 请求
    ↓
io_uring / Linux 内核执行 I/O
    ↓
完成事件进入 CQE
    ↓
EventLoop 处理 CQE
    ↓
恢复协程或执行回调
~~~

与传统 epoll + 非阻塞 read/write 的区别是：epoll 通常只通知“现在可以读写”，应用还要自己调用 read/write；io_uring 则直接提交读写请求，完成后通过 CQE 返回结果。

## 2. 总体分层

### 2.1 应用入口层

主要入口：

- src/test.cpp：HTTP Echo 服务；
- recommend/recommend_server.cpp：推荐服务 Demo；
- client/test_client.cpp：功能和异常测试客户端；
- bench/echo_bench.cpp：Echo 压测客户端。

应用层负责读取配置、初始化日志和内存池、创建主 EventLoop、创建 TcpServer、注册业务回调并进入主循环。

### 2.2 服务器组织层

- TcpServer：服务器总控和连接生命周期管理；
- Acceptor：监听端口并接收新连接；
- EventLoopThreadPool：创建和管理工作线程；
- EventLoopThread：在线程中持有并运行一个工作 EventLoop。

### 2.3 事件和 I/O 层

- EventLoop：封装 io_uring、CQE 处理、任务队列和 eventfd 唤醒；
- IoContext：绑定 io_uring 的 user_data，保存操作类型、结果和协程句柄；
- AsyncReadAwaitable：把异步读包装成 co_await；
- AsyncWriteAwaitable：把异步写包装成 co_await；
- AsyncSleepAwaitable：把 io_uring timeout 包装成 co_await。

### 2.4 连接和数据层

- TcpConnection：单条 TCP 连接的状态、读写、超时、关闭和业务回调；
- Socket：socket fd 和 socket 选项封装；
- InetAddress：IPv4 地址封装；
- Buffer：输出数据缓冲区和协议累积缓冲区。

### 2.5 公共设施层

- LockFreeQueue：跨线程任务队列和异步日志队列；
- MemoryPool / HashBucket：小对象内存池；
- Logger：异步日志和日志轮转；
- Config：INI 风格配置解析。

## 4. TcpServer 的职责和成员

TcpServer 是框架对外的服务器总控类。它不直接实现 HTTP、RPC 或推荐业务，而是组织底层组件并管理连接生命周期。

主要成员：

| 成员 | 作用 |
| --- | --- |
| loop_ | 主 EventLoop，负责服务器主线程中的监听和服务器级任务 |
| name_ | 服务器名称，用于标识和生成连接名称 |
| ipPort_ | 监听地址字符串，用于日志和连接名称 |
| acceptor_ | 独占的 Acceptor，负责监听和 accept |
| connectionCallback_ | 用户设置的连接建立后业务回调 |
| started_ | 防止服务器重复启动 |
| nextConnId_ | 生成连接编号 |
| connections_ | 当前活动连接表，保存连接名称到 TcpConnection 的映射 |
| threadPool_ | 工作线程和工作 EventLoop 的管理器 |
| readTimeout_ | 新连接默认的读超时时间 |

对外操作：

~~~text
构造 TcpServer
    → 设置监听地址和服务器名称
setThreadNum()
    → 设置工作线程数量
setEventLoopOptions()
    → 设置工作 EventLoop 的 io_uring、注册缓冲区和队列参数
setReadTimeout()
    → 设置新连接的读超时
setConnectionCallback()
    → 设置连接建立后的业务入口
start()
    → 启动工作线程并开始监听
~~~

主要内部操作：

- newConnection()：将 accept 得到的 fd 包装成 TcpConnection 并分配给工作 EventLoop；
- removeConnection()：从活动连接表中移除连接，并安排连接最终销毁。

## 5. Acceptor 与 TcpServer 的解耦

Acceptor 的职责仅限于：

~~~text
创建监听 socket
    ↓
bind/listen
    ↓
提交 accept 请求
    ↓
得到新连接 fd 和对端地址
    ↓
通过回调通知外部
~~~

它不负责创建 TcpConnection、选择工作线程、管理活动连接表或执行业务连接回调。

Acceptor 使用以下回调类型：

~~~cpp
using NewConnectionCallback =
    std::function<void(int sockfd,
                       const InetAddress &peerAddr)>;
~~~

TcpServer 构造时注册：

~~~cpp
acceptor_->setNewConnectionCallback(
    std::bind(&TcpServer::newConnection,
              this,
              std::placeholders::_1,
              std::placeholders::_2));
~~~

其语义等价于：

~~~cpp
[this](int sockfd, const InetAddress &peerAddr) {
    this->newConnection(sockfd, peerAddr);
}
~~~

调用链：

~~~text
Acceptor 收到连接
    → newConnectionCallback_(sockfd, peerAddr)
    → TcpServer::newConnection(sockfd, peerAddr)
~~~

本框图说明：这是“Acceptor 通过回调通知 TcpServer”的职责解耦框图。Acceptor 产生事件，TcpServer 决定事件如何被组织和管理。

## 6. EventLoop、EventLoopThread 和 EventLoopThreadPool

### 6.1 三个类的分工

这三个类组成“事件循环、单线程封装、多线程组织”三层结构：

| 类 | 核心职责 | 不负责什么 |
|---|---|---|
| `EventLoop` | 驱动 io_uring、分发 CQE、恢复协程、执行跨线程任务 | 不创建工作线程，不选择连接归属 |
| `EventLoopThread` | 封装一个 `std::thread`，在该线程栈上创建并运行一个 `EventLoop` | 不管理多个线程，不知道 TCP 连接和业务逻辑 |
| `EventLoopThreadPool` | 创建多个 `EventLoopThread`，收集工作 `EventLoop*`，轮询选择连接归属 | 不直接执行 I/O，不拥有主 `EventLoop` |

~~~mermaid
flowchart LR
    POOL["EventLoopThreadPool<br/>组织和调度"]
    THREAD["EventLoopThread<br/>单线程生命周期"]
    LOOP["EventLoop<br/>I/O 执行单元"]
    RING["io_uring<br/>SQ / CQ"]
    TASK["协程和任务队列"]

    POOL -->|"创建多个"| THREAD
    THREAD -->|"线程内创建一个"| LOOP
    LOOP -->|"拥有"| RING
    LOOP -->|"恢复和执行"| TASK
~~~

本框图说明：这是“`EventLoopThreadPool` 组织多个单线程封装，`EventLoopThread` 在线程中创建 `EventLoop`，`EventLoop` 再驱动 io_uring 和上层任务”的三层职责框图。

### 6.2 EventLoop：线程绑定的 I/O 执行单元

一个 `EventLoop` 内部拥有：

- 独立的 io_uring ring；
- eventfd 唤醒通道；
- `pendingFunctors_` 跨线程任务队列；
- io_uring 注册缓冲区及可用索引栈；
- CQE 分发、协程恢复和回调调用逻辑；
- 构造时记录的所属线程 ID。

它的主要操作是：

| 操作 | 功能 |
|---|---|
| `loop()` | 提交 SQE、等待 CQE、批量处理完成事件和任务队列 |
| `runInLoop()` | 当前就在所属线程时立即执行，否则转为队列投递 |
| `queueInLoop()` | 任务入队并在必要时通过 eventfd 唤醒目标线程 |
| `handleCompletionEvent()` | 根据 `IoContext` 恢复协程或调用 handler |
| `quit()` | 设置退出标志，必要时唤醒阻塞中的循环 |

~~~mermaid
flowchart TB
    LOOP["EventLoop::loop"]
    READY{"SQ 有待提交项"}
    SUBMIT["提交 SQE"]
    WAIT["等待 CQE"]
    CQE["分发全部 CQE"]
    CORO["恢复协程<br/>或执行 handler"]
    FUNCTOR["执行 pendingFunctors"]
    QUIT{"quit 已请求"}

    LOOP --> READY
    READY -- "是" --> SUBMIT --> WAIT
    READY -- "否" --> WAIT
    WAIT --> CQE --> CORO --> FUNCTOR --> QUIT
    QUIT -- "否" --> READY
    QUIT -- "是" --> EXIT["退出循环"]
~~~

本框图说明：这是“一个 `EventLoop` 在所属线程中提交 I/O、等待和分发完成事件、恢复协程并执行跨线程任务”的单次循环框图。

`EventLoop` 不主动创建线程。主 `EventLoop` 由应用入口在主线程中创建，工作 `EventLoop` 由 `EventLoopThread::threadFunc()` 在各工作线程栈上创建。

### 6.3 EventLoopThread：一个管理对象对应一个工作线程

`EventLoopThread` 是线程生命周期封装，它本身不是操作系统线程，而是包含一个 `std::thread` 成员的 C++ 管理对象：

~~~mermaid

    ELT["EventLoopThread 对象"]
    STD["thread_"]
    WORKER["工作执行线程"]
    STACK["工作线程栈"]
    ELOOP["EventLoop loop"]
    PTR["loop_<br/>非拥有指针"]

    OWNER -->|"拥有"| ELT
    ELT -->|"成员"| STD

~~~

本框图说明：这是“启动线程拥有 `EventLoopThread` 管理对象，对象内的 `thread_` 启动工作执行线程，工作线程栈上才存在真正的 `EventLoop`，`loop_` 只保存其地址”的对象与线程关系框图。

核心成员分工如下：

| 成员 | 作用 |
|---|---|
| `thread_` | 持有真实工作线程的 `std::thread` 句柄 |
| `loop_` | 工作线程将栈上 `EventLoop` 地址发布到这里，不负责删除对象 |
| `mutex_ / cond_` | 让启动线程等待工作 `EventLoop` 创建完成 |
| `options_` | 传入工作 `EventLoop` 构造函数的配置副本 |
| `callback_` | 在工作线程内、`loop.loop()` 前执行一次的可选初始化回调 |

### 6.4 EventLoopThreadPool：多工作线程组织器

`EventLoopThreadPool` 由 `TcpServer` 按值持有。它保存主 `EventLoop` 的非拥有指针，独占拥有多个 `EventLoopThread`，并保存每个工作 `EventLoop` 的非拥有指针：

~~~mermaid

    POOL["EventLoopThreadPool"]
    BASE["baseLoop_<br/>主 EventLoop"]
    THREADS["threads_<br/>unique_ptr 数组"]
    LOOPS["loops_<br/>EventLoop 指针数组"]
    T0["EventLoopThread 0"]
    T1["EventLoopThread 1"]
    L0["Worker EventLoop 0"]
    L1["Worker EventLoop 1"]

    SERVER -->|"按值拥有"| POOL
    POOL -->|"非拥有"| BASE
    POOL --> THREADS
    THREADS -->|"独占拥有"| T0
    THREADS -->|"独占拥有"| T1
    POOL --> LOOPS
    LOOPS -->|"观察"| L0
    LOOPS -->|"观察"| L1
    T0 -->|"线程内运行"| L0
    T1 -->|"线程内运行"| L1
~~~

本框图说明：这是“`TcpServer` 拥有线程池，线程池通过 `threads_` 独占拥有线程管理对象，通过 `baseLoop_` 和 `loops_` 非拥有地访问主与工作 `EventLoop`”的所有权框图。

`threads_` 和 `loops_` 必须区分：

~~~text
threads_  -> 独占拥有 EventLoopThread，决定工作线程生命周期
loops_    -> 只保存工作 EventLoop 地址，不能 delete
baseLoop_ -> 只观察应用入口创建的主 EventLoop
~~~

`threads_.push_back(std::move(t))` 只移动 `unique_ptr` 所有权，不搬移堆上的 `EventLoopThread` 对象。因此工作线程捕获的 `this` 指针保持有效，即使 `threads_` 扩容也不会改变对象地址。

线程池按顺序启动工作线程。每次 `t->startLoop()` 都会等到对应工作 `EventLoop` 地址发布后才返回，然后线程池再创建下一个工作线程。

### 6.6 为什么两个线程访问同一个 `EventLoopThread`

`startLoop()` 在启动线程中执行，它将当前管理对象的 `this` 指针传给新线程：

~~~cpp
thread_ = std::thread(
    std::bind(&EventLoopThread::threadFunc, this));
~~~

`std::thread` 只复制 `this` 指针值，不复制整个 `EventLoopThread` 对象。

~~~mermaid
flowchart TB
    OBJ["EventLoopThread 对象<br/>唯一一份"]
    START["启动线程<br/>startLoop"]
    WORK["工作线程<br/>threadFunc"]
    THIS1["this = 对象地址"]
    THIS2["this = 同一地址"]
    SHARED["loop_ / mutex_ / cond_<br/>共享成员"]
    WLOOP["工作栈 EventLoop"]

    START --> THIS1 --> OBJ
    WORK --> THIS2 --> OBJ
    OBJ --> SHARED
    WORK --> WLOOP
    WLOOP -->|"地址写入 loop_"| SHARED
    SHARED -->|"启动线程读取"| START
~~~

本框图说明：这是“启动线程和工作线程通过相同 `this` 访问唯一的 `EventLoopThread` 管理对象，工作线程将自己栈上 `EventLoop` 地址写入共享成员 `loop_`，启动线程再读取该地址”的共享对象框图。

`loop_` 不是启动线程自己的 `EventLoop`。指针属于哪个 C++ 管理对象，和它指向哪个线程中的对象是两件事。`loop_` 的目标由工作线程执行的 `loop_ = &loop` 决定。

### 6.7 条件变量如何发布 `EventLoop*`


本框图说明：这是“启动线程的 `wait()` 在休眠时释放锁，工作线程在同一互斥锁保护下发布 `loop_` 地址并通知，启动线程醒来后重新加锁并复制地址”的条件变量同步时序图。

`cond_.wait(lock, predicate)` 会重复检查谓词，因此既能处理虚假唤醒，也能处理工作线程在启动线程真正进入等待前就已经发布地址的情况。

### 6.8 `ThreadInitCallback` 的解耦作用

线程池和单线程封装都定义了：

~~~cpp
using ThreadInitCallback = std::function<void(EventLoop *)>;
~~~

这是两个作用域中对同一底层类型的别名，不是两种不同类型，也不会自动创建两个回调对象。

~~~mermaid
flowchart LR
    APP["调用者可选回调"]
    START["ThreadPool::start cb"]
    MAKE["创建 EventLoopThread"]
    SAVE["callback_ = cb"]
    CREATE["工作线程构造 EventLoop"]
    RUN["callback_(&loop)"]
    LOOP["loop.loop()"]

    APP --> START --> MAKE --> SAVE --> CREATE --> RUN --> LOOP
~~~

本框图说明：这是“调用者将初始化回调传给线程池，线程池把回调分发给每个 `EventLoopThread`，工作线程在 `EventLoop` 构造后、事件循环启动前执行一次”的回调传播框图。

### 6.12 跨线程任务投递的解耦

线程池只决定连接归属，不直接切换执行线程。真正将操作转移到目标工作线程的是 `EventLoop::runInLoop()` 和 `queueInLoop()`。

~~~mermaid
sequenceDiagram
    participant M as 主 EventLoop
    participant S as TcpServer
    participant P as ThreadPool
    participant W as Worker EventLoop
    participant C as TcpConnection

    M->>S: newConnection(connfd)
    S->>P: getNextLoop()
    P-->>S: Worker EventLoop 指针
    S->>C: 创建并绑定 Worker
    S->>W: runInLoop(connectEstablished)
    W->>W: 任务入 pendingFunctors
    W->>W: eventfd 唤醒
    W->>C: 在工作线程执行
~~~

本框图说明：这是“主线程中的 `TcpServer` 向线程池请求一个目标 `EventLoop`，连接对象绑定该 Loop 后，通过 `runInLoop()`、任务队列和 eventfd 在正确工作线程执行 `connectEstablished()`”的跨线程投递时序图。

这样的解耦意味着：

1. `EventLoopThreadPool` 只返回目标 `EventLoop*`，不知道具体任务。
2. `EventLoopThread` 只管理线程创建和退出，不知道 `TcpConnection`。
3. `EventLoop` 只调度可调用对象，不知道它是建立连接、关闭连接还是业务任务。
4. `TcpServer` 组装这些接口，实现“选择归属线程”和“在归属线程执行连接状态变更”。

本框图说明：这是“线程池销毁时由 `threads_` 自动销毁线程管理对象，`EventLoopThread` 请求所属 Loop 退出并等待工作线程，工作栈上 `EventLoop` 随线程函数返回而析构”的退出生命周期框图。

`loops_` 中的指针不需要也不能被线程池 `delete`，因为真正的 `EventLoop` 是 `threadFunc()` 栈对象。工作线程退出后，对应的 `loops_` 指针立即失效。

### 6.14 当前实现的约束与风险

1. `getNextLoop()` 修改普通 `int next_`，没有加锁；当前约束是只由主 `EventLoop` 线程调用。
2. `start()` 会设置 `started_`，但没有利用该标志阻止重复启动。
3. `baseLoop_`、`loops_` 和 `EventLoopThread::loop_` 都是非拥有指针，使用者必须遵守所指对象的生命周期。
4. `startLoop()` 在启动线程中调用 `loop->initRegisteredBuffers()`，但工作线程在发出 `notify_one()` 后可以立即进入 `loop.loop()`；两个线程可能并发访问同一 `ring_`。
5. 注册缓冲区初始化应移到 `threadFunc()` 中，在发布 `loop_` 地址和进入 `loop.loop()` 之前完成；也可以通过非空 `ThreadInitCallback` 在工作线程中执行。
6. `EventLoopThread` 析构函数只在 `loop_ != nullptr` 时调用 `join()`；如果线程已返回但 `thread_` 仍为 joinable，`std::thread` 析构可能触发 `std::terminate`。更稳妥的判断应以 `thread_.joinable()` 为准。
7. 当前 `loop_` 的读写并非所有位置都在同一互斥锁保护下，析构与工作线程退出同时发生时需要额外的生命周期同步。

推荐的初始化顺序是：

~~~text
工作线程构造 EventLoop
    -> 工作线程初始化注册缓冲区
    -> 工作线程执行 ThreadInitCallback
    -> 在 mutex_ 保护下发布 loop_
    -> notify_one()
    -> 进入 EventLoop::loop()
~~~

## 8. TcpConnection 的职责和关联

TcpConnection 表示一条具体 TCP 连接，是业务协程与底层 I/O 之间的主要接口。

### 8.1 连接归属

~~~cpp
EventLoop *loop_;
Socket socket_;
InetAddress localAddr_;
InetAddress peerAddr_;
~~~

表示连接属于哪个 EventLoop、使用哪个 socket fd，以及本地和对端地址。

### 8.2 连接状态

~~~cpp
std::atomic<TcpConnectionState> state_;
~~~

状态包括：

~~~text
kConnecting
kConnected
kDisconnecting
kDisconnected
~~~

### 8.3 I/O 上下文

~~~cpp
IoContext readContext_;
IoContext writeContext_;
IoContext timeoutContext_;
~~~

每个上下文用于把 I/O 操作绑定到 io_uring 的 user_data，并保存操作类型、fd、注册缓冲区索引、协程句柄、完成结果和传统回调。

### 8.4 数据缓冲

~~~cpp
void *curReadBuffer_;
size_t curReadBufferSize_;
Buffer outputBuffer_;
~~~

当前读缓冲区通常来自 EventLoop 的注册缓冲区；outputBuffer_ 保存待发送数据。

### 8.5 业务和关闭回调

~~~cpp
ConnectionCallback connectionCallback_;
CloseCallback closeCallback_;
~~~

connectionCallback_ 在连接建立后调用一次，通常用于启动业务协程；closeCallback_ 在关闭流程中通知 TcpServer 移除连接。

## 9. connectionCallback_ 的传播关系

业务层先设置 TcpServer 的回调：

~~~cpp
server.setConnectionCallback(
    [](const std::shared_ptr<TcpConnection> &conn) {
        httpPingPongTask(conn);
    });
~~~

TcpServer 保存这个回调。创建新连接时，再设置给具体连接：

~~~cpp
conn->setConnectionCallback(connectionCallback_);
~~~

传播链：

~~~text
业务层回调
    → TcpServer::connectionCallback_
    → TcpConnection::connectionCallback_
    → connectEstablished() 中调用
    → 启动 HTTP/RPC/自定义业务协程
~~~

默认情况下，一个 TcpServer 的所有连接共享同一个连接建立回调。若要根据连接属性执行不同业务，应在回调内部进行分流，或者在创建连接后单独覆盖连接回调。

## 10. 协程 I/O 关系

业务层调用：

~~~cpp
int n = co_await conn->asyncRead(4096);
int written = co_await conn->asyncSend(response);
~~~

读操作链路：

~~~text
AsyncReadAwaitable
  → await_suspend 保存协程句柄
  → TcpConnection 提交 read SQE
  → EventLoop 提交 io_uring 请求
  → 内核完成读操作
  → EventLoop 收到 CQE
  → IoContext 保存 result_
  → 恢复协程
  → await_resume 返回字节数
~~~

写操作链路类似，完成后还要推进 outputBuffer_ 的读位置。

## 11. 连接关闭流程

~~~text

    ↓

    ↓
TcpConnection::handleClose()
    ↓
调用 closeCallback_
    ↓
TcpServer::removeConnection(conn)
    ↓
主 EventLoop 执行 connections_.erase(name)
    ↓
连接所属 Worker EventLoop 执行 connectDestroyed()
~~~

## 12. 组件之间的解耦方式

### 12.1 Acceptor 与 TcpServer：回调解耦

~~~text
Acceptor
    → NewConnectionCallback
    → TcpServer::newConnection()
~~~

Acceptor 只产生新连接事件，不知道连接该如何管理，因此可以被其他连接管理器复用。

### 12.2 TcpServer 与业务：ConnectionCallback 解耦

~~~text
TcpServer
    → ConnectionCallback
    → 业务协程/业务处理函数
~~~

TcpServer 不知道连接是 HTTP、RPC 还是自定义协议。

### 12.3 EventLoop 与跨线程任务：runInLoop/queueInLoop 解耦

~~~text
调用方
    → runInLoop/queueInLoop
    → 目标 EventLoop 任务队列
    → 目标线程执行
~~~

### 12.4 协程与 io_uring：Awaitable + IoContext 解耦

业务只看到：

~~~cpp
co_await conn->asyncRead(...);
~~~

具体的 SQE、CQE、协程句柄和结果转移由 Awaitable、IoContext 和 EventLoop 协作完成。

### 12.5 协议编解码器与网络连接：Buffer 接口解耦

~~~text
TcpConnection 提供数据/Buffer
    → Codec::decode()
    → 业务对象
    → Codec::encode()
    → output Buffer
    → asyncWrite()
~~~

当前默认的 proactor_test 和 recommend_server 使用各自的手写 HTTP 解析器，并没有实际调用 HttpCodec；codec 是可选组件。

### 12.6 跨线程任务投递图


### 12.7 LockFreeQueue 无锁任务队列设计

`EventLoop` 使用如下成员保存跨线程任务：

~~~cpp
LockFreeQueue<Functor> pendingFunctors_;
~~~

`LockFreeQueue<T>` 被设计为固定容量的 MPMC（Multi-Producer Multi-Consumer，多生产者多消费者）环形队列。当前项目中可能有多个线程向同一个 `EventLoop` 投递任务，而通常只有该 `EventLoop` 所属线程执行出队，因此实际使用更接近 MPSC；队列本身仍提供 MPMC 的竞争控制。

这里的“无锁”不表示没有同步，也不表示所有线程可以同时随意修改同一份数据。它使用三套原子协议代替互斥锁：

| 并发机制 | 负责的问题 |
|---|---|
| `enqueuePos_` 上的 CAS | 多个生产者中，只有一个能取得某个逻辑入队位置 |
| `dequeuePos_` 上的 CAS | 多个消费者中，只有一个能取得某个逻辑出队位置 |
| 每个 `Slot::sequence` 的 acquire/release | 表示槽位轮次与读写状态，并在生产者和消费者之间发布 `data` |

#### 12.7.1 核心数据结构

~~~cpp
struct Slot
{
    std::atomic<size_t> sequence;
    T data;
};

alignas(64) std::atomic<size_t> enqueuePos_;
alignas(64) std::atomic<size_t> dequeuePos_;
std::vector<Slot> buffer_;
size_t bufferMask_;
~~~

各成员的职责如下：

- `enqueuePos_`：下一个生产者要争抢的逻辑位置，只在入队 CAS 成功后递增。
- `dequeuePos_`：下一个消费者要争抢的逻辑位置，只在出队 CAS 成功后递增。
- `buffer_`：固定大小的物理槽位数组，构造完成后不再扩容，保证 `Slot*` 地址稳定。
- `bufferMask_`：容量减一，用于把持续递增的逻辑位置映射到有限的物理槽位。
- `sequence`：槽位的“轮次 + 阶段”标记，不只表示空或满。
- `data`：真正保存的任务；它不是原子变量，而是依靠位置 CAS、`sequence` 和所有权交接安全访问。

`alignas(64)` 尽量把生产者频繁修改的 `enqueuePos_` 和消费者频繁修改的 `dequeuePos_` 放到不同缓存行，减少伪共享。它只优化性能，不承担正确性保证。

#### 12.7.2 逻辑位置与物理槽位

`enqueuePos_` 和 `dequeuePos_` 是持续递增的逻辑票号，不会在到达队列容量时主动归零。队列容量会向上取整为 2 的幂，因此可以使用：

~~~cpp
size_t index = pos & bufferMask_;
Slot *slot = &buffer_[index];
~~~

代替：

~~~cpp
size_t index = pos % buffer_.size();
~~~

例如容量为 4，`bufferMask_ = 3`：

| 逻辑位置 `pos` | `pos & 3` | 物理槽位 |
|---:|---:|---|
| 0 | 0 | `buffer_[0]` |
| 1 | 1 | `buffer_[1]` |
| 2 | 2 | `buffer_[2]` |
| 3 | 3 | `buffer_[3]` |
| 4 | 0 | `buffer_[0]` |
| 5 | 1 | `buffer_[1]` |
| 8 | 0 | `buffer_[0]` |

~~~mermaid
flowchart LR
    POS[持续递增的逻辑位置 pos]
    MASK[pos 与 bufferMask_ 按位与]
    INDEX[有限范围的物理下标 index]
    SLOT["buffer_[index]"]
    SEQ[sequence 区分该槽位属于哪一轮]

    POS --> MASK --> INDEX --> SLOT --> SEQ
~~~

本框图说明：这是“持续递增的逻辑票号如何映射到重复使用的物理槽位，并由 `sequence` 区分复用轮次”的映射图。

#### 12.7.3 sequence 的状态编码

设：

~~~text
N   = buffer_.size()
pos = 当前逻辑位置
i   = pos 映射到的物理槽位下标
~~~

一个槽位的通用状态规则是：

| 阶段 | `sequence` 值 | 谁可以继续操作 |
|---|---:|---|
| 当前轮可写 | `pos` | 当前轮生产者 |
| 当前轮写完、可读 | `pos + 1` | 当前轮消费者 |
| 当前轮读完、下一轮可写 | `pos + N` | 下一轮生产者 |

构造时：

~~~cpp
buffer_[i].sequence.store(i, std::memory_order_relaxed);
~~~

表示槽位 `i` 已准备好接收第一轮逻辑位置 `i` 的数据。

以容量 4 的 `buffer_[0]` 为例：

~~~text
sequence = 0：逻辑位置 0 可写
sequence = 1：逻辑位置 0 已写完，可读
sequence = 4：逻辑位置 0 已读完，逻辑位置 4 可写
sequence = 5：逻辑位置 4 已写完，可读
sequence = 8：逻辑位置 4 已读完，逻辑位置 8 可写
~~~

~~~mermaid
stateDiagram-v2
    [*] --> Writable0: 初始化 sequence=0
    Writable0 --> Readable0: 生产者写完<br/>release store sequence=1
    Readable0 --> Writable4: 消费者读完<br/>release store sequence=4
    Writable4 --> Readable4: 生产者写完<br/>release store sequence=5
    Readable4 --> Writable8: 消费者读完<br/>release store sequence=8
~~~

本框图说明：这是“容量为 4 时，`buffer_[0]` 的 `sequence` 如何同时表达轮次和可写/可读阶段”的状态图。

如果消费者读完后把 `sequence` 重置成 0，下一轮逻辑位置 4 的生产者会计算出 `0 - 4 < 0`，错误地认为槽位仍未释放。因此必须写成 `pos + N`，直接标记下一轮的逻辑票号。

#### 12.7.4 入队逻辑条件

生产者读取：

~~~cpp
size_t pos = enqueuePos_.load(std::memory_order_relaxed);
Slot *slot = &buffer_[pos & bufferMask_];
size_t seq = slot->sequence.load(std::memory_order_acquire);
intptr_t dif = static_cast<intptr_t>(seq) - static_cast<intptr_t>(pos);
~~~

生产者期待 `sequence == pos`，因此 `dif` 的含义为：

| `dif = seq - pos` | 槽位状态 | 处理方式 |
|---:|---|---|
| `0` | 槽位正好可供当前逻辑位置写入 | CAS 争抢 `enqueuePos_` |
| `< 0` | 槽位仍停留在旧一轮，旧数据尚未消费或释放 | 返回 `false`，队列表现为满 |
| `> 0` | 槽位已经进入更靠后的状态，当前线程保存的 `pos` 过时 | 重新读取 `enqueuePos_` |

容量为 4、当前 `pos = 4` 时：

- `seq = 4`：`dif = 0`，槽位已由逻辑位置 0 的消费者释放，可以写逻辑位置 4。
- `seq = 1`：`dif = -3`，逻辑位置 0 已写完但还没有释放，不能覆盖。
- `seq = 5`：`dif = 1`，其他生产者已经完成逻辑位置 4，当前线程的 `pos` 已经过时。

~~~mermaid
flowchart TD
    START[读取 enqueuePos_ 得到 pos]
    MAP["定位 slot = buffer_[pos 与 mask]"]
    LOAD[acquire 读取 slot.sequence]
    DIF[计算 dif = seq - pos]
    ZERO{dif 是否为 0}
    NEG{dif 是否小于 0}
    CAS{CAS: enqueuePos_ 从 pos 改为 pos+1}
    REFRESH[重新获取最新 pos]
    FULL[返回 false: 队列表现为满]
    WRITE[独占槽位并写入 data]
    PUBLISH[release store sequence = pos+1]
    OK[返回 true]

    START --> MAP --> LOAD --> DIF --> ZERO
    ZERO -->|是| CAS
    ZERO -->|否| NEG
    NEG -->|是| FULL
    NEG -->|否| REFRESH --> MAP
    CAS -->|失败| MAP
    CAS -->|成功| WRITE --> PUBLISH --> OK
~~~

本框图说明：这是“生产者如何检查 `sequence`、使用 CAS 独占逻辑入队位置、写入数据并发布为可读”的入队流程图。

#### 12.7.5 出队逻辑条件

消费者读取：

~~~cpp
size_t pos = dequeuePos_.load(std::memory_order_relaxed);
Slot *slot = &buffer_[pos & bufferMask_];
size_t seq = slot->sequence.load(std::memory_order_acquire);
intptr_t dif = static_cast<intptr_t>(seq) - static_cast<intptr_t>(pos + 1);
~~~

消费者期待 `sequence == pos + 1`，因为生产者写完后通过 `pos + 1` 发布可读状态：

| `dif = seq - (pos + 1)` | 槽位状态 | 处理方式 |
|---:|---|---|
| `0` | 当前逻辑位置的数据已经完整发布 | CAS 争抢 `dequeuePos_` |
| `< 0` | 生产者尚未发布当前数据 | 返回 `false`，队列表现为空 |
| `> 0` | 该位置已被其他消费者推进，当前线程保存的 `pos` 过时 | 重新读取 `dequeuePos_` |

容量为 4、当前消费者 `pos = 0` 时：

- `seq = 1`：`dif = 0`，逻辑位置 0 已写完，可以读取。
- `seq = 0`：`dif = -1`，生产者尚未发布数据。
- `seq = 4`：`dif = 3`，逻辑位置 0 已被其他消费者读完并释放，当前 `pos` 过时。

~~~mermaid
flowchart TD

    MAP["定位 slot = buffer_[pos 与 mask]"]
    LOAD[acquire 读取 slot.sequence]
    DIF["计算 dif = seq - (pos + 1)"]

    NEG{dif 是否小于 0}
    CAS{CAS: dequeuePos_ 从 pos 改为 pos+1}

    ZERO -->|否| NEG
~~~

本框图说明：这是“消费者如何确认数据已发布、使用 CAS 独占逻辑出队位置、读取数据并把槽位释放给下一轮生产者”的出队流程图。

#### 12.7.6 CAS 如何解决多线程竞争

多个线程可以同时通过 acquire load 观察到同一个 `sequence` 状态。原子读取只保证状态读取不撕裂，不能保证只有一个线程看见它。因此 `sequence` 负责判断“现在能不能操作”，位置计数器上的 CAS 才负责决定“由谁操作”。

假设两个生产者都读到 `enqueuePos_ = 10`，并且都发现槽位可写。它们同时尝试：

~~~cpp
enqueuePos_.compare_exchange_weak(
    pos,
    pos + 1,
    std::memory_order_relaxed);
~~~

对同一个原子变量，`10 -> 11` 只能有一个 CAS 成功：

~~~mermaid
sequenceDiagram
    participant P1 as 生产者 A
    participant P2 as 生产者 B
    participant EP as enqueuePos_
    participant S as 目标 Slot

    P1->>EP: load，得到 pos=10
    P2->>EP: load，也得到 pos=10
    P1->>S: acquire load sequence，发现可写
    P2->>S: acquire load sequence，也发现可写
    P1->>EP: CAS 10 -> 11
    EP-->>P1: 成功，A取得逻辑位置10
    P2->>EP: CAS 10 -> 11
    EP-->>P2: 失败，并把当前值11写回P2的pos
    P1->>S: 写data并release发布
    P2->>P2: 使用更新后的pos重新尝试
~~~

本框图说明：这是“多个生产者即使同时看到槽位可写，也只有一个能通过 `enqueuePos_` CAS 获得该逻辑位置”的竞争时序图。多个消费者竞争 `dequeuePos_` 时原理相同。

`compare_exchange_weak(expected, desired)` 的行为是：

- 当前原子值等于 `expected`：尝试写入 `desired` 并返回 `true`。
- 当前原子值不等于 `expected`：不写入，把实际当前值写回 `expected` 并返回 `false`。
- `weak` 允许偶发的伪失败，因此必须在循环中重新检查和尝试。

这里的 `pos` 同时承担 CAS 的 `expected` 参数。CAS 失败后，`pos` 可能已经被自动更新为位置计数器的当前值。

位置 CAS 使用 `memory_order_relaxed` 是因为它只负责分配唯一逻辑票号，不负责发布 `data`。即使 relaxed load 暂时观察到旧票号，CAS 也会按原子变量的实际修改顺序验证；旧 `expected` 会失败并得到更新。`data` 的跨线程可见性由 `sequence` 的 acquire/release 保证。

#### 12.7.7 release 与 acquire 的双向配合

`sequence` 上存在两组跨线程同步：

| 发布方 | 接收方 | 发布的含义 |
|---|---|---|
| 生产者 `store(pos + 1, release)` | 消费者 `load(acquire)` | `data` 已完整写入，可以读取 |
| 消费者 `store(pos + N, release)` | 下一轮生产者 `load(acquire)` | `data` 已读取完成，可以覆盖 |

生产者发布数据：

~~~cpp
slot->data = std::forward<U>(data);
slot->sequence.store(pos + 1, std::memory_order_release);
~~~

消费者接收数据：

~~~cpp
size_t seq = slot->sequence.load(std::memory_order_acquire);
// 确认 seq == pos + 1 并通过 dequeuePos_ CAS 后
data = std::move(slot->data);
~~~

当 acquire load 实际观察到对应 release store 发布的值时，形成：

~~~text
生产者写 slot->data
        happens-before
消费者读 slot->data
~~~

消费者释放槽位与下一轮生产者接收槽位同理：

~~~text
消费者读完或移动 slot->data
        happens-before
下一轮生产者覆盖 slot->data
~~~

~~~mermaid
sequenceDiagram
    participant P0 as 当前轮生产者 pos=0
    participant S as buffer_[0] / sequence
    participant C0 as 当前轮消费者 pos=0
    participant P4 as 下一轮生产者 pos=4

    Note over S: 初始 sequence=0，可写
    P0->>S: acquire load sequence=0
    P0->>S: 写入 data=A
    P0->>S: release store sequence=1
    Note over S: data=A 已发布，可读
    C0->>S: acquire load sequence=1
    C0->>S: 移出 data=A
    C0->>S: release store sequence=4
    Note over S: 当前轮已读完，下一轮可写
    P4->>S: acquire load sequence=4
    P4->>S: 覆盖写入 data=B
    P4->>S: release store sequence=5
~~~

本框图说明：这是“生产者发布数据给消费者，以及消费者再把槽位释放给下一轮生产者”的双向 acquire/release 交接时序图。

`acquire` 不会等待 `release`，也不会阻塞。如果消费者在生产者发布前读取到旧 `sequence`，它只会根据 `dif < 0` 返回队列空，不访问 `data`；之后再次调用出队并读到 `pos + 1` 时，才与生产者的 release 建立同步。第一次入队也没有上一轮消费者 release，它读取的是构造期初始化状态；正确性依赖队列完整构造后再通过线程启动或其他同步方式安全发布给工作线程。

#### 12.7.8 为什么 `data` 不需要是原子变量

`Slot::data` 的安全性来自分阶段的独占所有权：

~~~text
多个生产者观察槽位状态
    -> enqueuePos_ CAS 只允许一个生产者取得所有权
    -> 该生产者独占写 data
    -> release 发布可读

多个消费者观察可读状态
    -> dequeuePos_ CAS 只允许一个消费者取得所有权
    -> 该消费者独占读 data
    -> release 发布下一轮可写
~~~

因此不存在两个生产者同时写同一个 `data`，也不存在两个消费者同时移动同一个 `data`。生产者与消费者之间的非原子访问则由 `sequence` 的 release/acquire 建立 happens-before 关系。

需要同时满足以下前提：

- `buffer_` 构造后不再扩容或移动，否则其他线程保存的 `Slot*` 会失效。
- 队列析构前，所有访问线程必须已经停止。
- 所有访问必须经过队列协议，不能绕过接口直接读写 `Slot::data`。
- 队列对象必须完整构造后再安全发布给其他线程。

#### 12.7.9 sequence 与 ABA

如果槽位只有 `empty/full` 布尔状态，物理槽位重复使用时无法区分它属于逻辑位置 0、4 还是 8。旧状态从“可写”变为“可读”再变回“可写”，表面值相同，可能被误认为仍是原来的状态，这就是此处需要防范的 ABA 类问题。

`sequence` 不简单恢复为初始值，而是随逻辑轮次增长：

~~~text
容量为4的 buffer_[0]

第一轮：0 -> 1 -> 4
第二轮：4 -> 5 -> 8
第三轮：8 -> 9 -> 12
~~~

线程不仅看到“可写”，还会验证该状态是否恰好属于自己的 `pos`。旧轮次值与当前票号不相等，因此不会被误当成当前轮次。

#### 12.7.10 边界与实现约束

这套设计避免了互斥锁，但仍有以下边界：

- CAS 可能因竞争或伪失败而循环重试，无锁不等于没有等待或没有 CPU 消耗。
- 生产者领取位置后若长时间停顿、尚未 release 发布，消费者可能暂时将队头判断为空；消费者领取位置后停顿也可能延迟对应槽位复用。
- `empty()` 和 `size()` 分别读取两个 relaxed 原子值，不是同一时刻快照，只能用于观测和背压估算，不能代替 `enqueue()`/`dequeue()` 的返回值。
- `slot->data = ...` 如果在位置 CAS 成功后抛出异常，槽位无法发布，可能阻塞该逻辑位置。`T` 最好提供不抛异常的移动/复制赋值，或由队列增加异常恢复协议。
- `intptr_t` 应显式包含 `<cstdint>`；符号差值判断依赖活跃逻辑位置距离远小于整数范围的一半。
- `enqueuePos_`、`dequeuePos_` 和 `sequence` 最终会发生无符号回绕；64 位环境下通常极难遇到，但算法仍依赖计数器距离和回绕假设。
- 这是一种基于原子操作的固定容量 MPMC 队列；严格理论意义上的进度保证需要结合“线程领取位置后是否可能永久停顿”单独评价，不能只因没有 `mutex` 就断言所有操作始终 lock-free 前进。

综上，队列的并发正确性不是由某一个原子变量单独提供，而是由以下协议共同完成：

~~~text
逻辑位置持续递增
    + 2次幂掩码映射物理槽位
    + sequence区分轮次和读写阶段
    + 位置CAS分配唯一所有权
    + sequence release/acquire发布和接收data
~~~

~~~mermaid
    R[forceClose / 超时 / I/O 错误]
    S[TcpServer::removeConnection]
    T[主 EventLoop 移除连接记录]
    U[Worker EventLoop 执行 connectDestroyed]

    A --> B --> C
    C --> D
    C --> E
    C --> F
    C --> G --> H
    H --> I --> J --> K --> L --> M --> N --> O
    O --> P --> Q --> P
    P --> R
    R --> S
    S --> T
    S --> U
~~~

本框图说明：这是“从程序启动、服务器监听、新连接建立、业务协程运行，到连接关闭和资源清理”的完整生命周期框图。

## 14. 当前架构的关键约束

1. 一个 TcpConnection 应绑定到一个固定的 Worker EventLoop。
2. 连接的读写上下文、输出缓冲区和注册缓冲区索引应由所属线程操作。
3. TcpServer::connections_ 由主 EventLoop 统一维护。
4. Acceptor 不负责业务，只通过回调通知新连接。
5. connectionCallback_ 是连接建立后的业务入口，不是每条消息的回调。
6. HttpCodec/RpcCodec 虽然被编译进库，但不是默认服务的强制处理链。
7. EventLoopThreadPool 的工作线程数和每个工作 EventLoop 的配置应在启动前设置。

## 15. 总结

~~~text
EventLoop：驱动事件和完成队列
Acceptor：接收新连接
TcpServer：管理服务器和连接生命周期
EventLoopThreadPool：管理工作线程和 EventLoop
TcpConnection：管理单条连接
Awaitable：把异步 I/O 暴露为 co_await
IoContext：连接 io_uring 与协程/回调
Buffer：保存协议数据和待发送数据
业务回调：处理 HTTP、RPC 或自定义业务
~~~

整体链路是：

~~~text
Acceptor 产生连接事件
    → TcpServer 创建和分配 TcpConnection
    → TcpConnection 调用 connectionCallback_
    → 业务协程执行异步读写
    → EventLoop 处理 io_uring 完成事件
    → 关闭时 TcpServer 移除连接，所属 EventLoop 销毁连接
~~~

## 16. MemoryPool 与 HashBucket 小对象内存池

本项目的小对象内存池由 `include/MemoryPool.hpp` 和 `memory/MemoryPool.cpp` 实现。它的目标是将频繁的小内存分配从“每次调用 `malloc/free`”改为“批量申请大内存块，再从块中切分和复用固定大小的槽”。

这套设计需要先区分四个概念：

| 概念 | 含义 |
|---|---|
| `HashBucket` | 按申请字节数选择尺寸类别，管理全局共享的 `MemoryPool[64]` |
| `MemoryPool` | 只管理一种固定槽大小，例如专门管理 64 字节槽 |
| Block | `MemoryPool` 按需通过 `malloc(blockSize_)` 申请的大内存块，默认为 4096 字节 |
| Slot | 从 Block 中切分出的小块原始内存，用来存放一个小对象 |

### 16.1 总体层级和职责

~~~mermaid
flowchart TB
    APP["调用者<br/>newElement / useMemory"]
    HB["HashBucket<br/>尺寸分发器"]

    subgraph CLASSES["64 个尺寸类别"]
        P0["MemoryPool 0<br/>8 字节槽"]
        P1["MemoryPool 1<br/>16 字节槽"]
        P2["MemoryPool 2<br/>24 字节槽"]
        PN["MemoryPool 63<br/>512 字节槽"]
    end

    subgraph BLOCKS["某一个 MemoryPool 内部"]
        B3["Block 3<br/>4096 字节"]
        B2["Block 2<br/>4096 字节"]
        B1["Block 1<br/>4096 字节"]
        S1["Slot"]
        S2["Slot"]
        SN["Slot ..."]
    end

    APP --> HB
    HB --> P0
    HB --> P1
    HB --> P2
    HB --> PN
    P2 --> B3
    B3 --> B2 --> B1
    B3 --> S1
    B3 --> S2
    B3 --> SN
~~~

本框图说明：这是“调用者经 `HashBucket` 选择固定尺寸的 `MemoryPool`，每个池再管理多个 Block，每个 Block 包含多个同尺寸 Slot”的总体层级框图。

`HashBucket` 名称中虽然有 Hash，但当前实现并没有哈希表。它实际上是一个“尺寸类别分发器”。它也不是严格意义上的单例类：代码没有禁止构造 `HashBucket` 对象，只是所有对象和线程都共享唯一的静态数组：

~~~cpp
MemoryPool HashBucket::memoryPool[MEMORY_POOL_NUM];
~~~

这行定义会在程序启动期构造 64 个 `MemoryPool` 管理对象，但构造时只将 `firstBlock_` 等指针设为 `nullptr`，不会立即为每个池申请 4096 字节块。

### 16.2 尺寸分桶和路由

当 `size <= 512` 时，池索引的计算公式是：

~~~cpp
index = (size + 7) / 8 - 1;
~~~

它等价于将申请大小向上取整到 8 的倍数：

| 申请大小 | 池索引 | 槽大小 |
|---:|---:|---:|
| 1 ~ 8 | 0 | 8 |
| 9 ~ 16 | 1 | 16 |
| 17 ~ 24 | 2 | 24 |
| 505 ~ 512 | 63 | 512 |
| > 512 | 不进入池 | 直接 `malloc/free` |

~~~mermaid
flowchart TD
    REQ["useMemory size"] --> ZERO{"size 是 0"}
    ZERO -- "是" --> NULL["返回 nullptr"]
    ZERO -- "否" --> LARGE{"size 大于 512"}
    LARGE -- "是" --> SYS["malloc size"]
    LARGE -- "否" --> IDX["index = ceil(size / 8) - 1"]
    IDX --> PICK["选择 memoryPool[index]"]
    PICK --> ALLOC["MemoryPool::allocate"]
    SYS --> OUT["返回原始内存"]
    ALLOC --> OUT
~~~

本框图说明：这是“`HashBucket::useMemory()` 根据申请大小选择固定槽内存池，超过 512 字节时退回系统分配器”的尺寸路由框图。

例如申请 20 字节：

~~~text
index = (20 + 7) / 8 - 1 = 2
slotSize = (2 + 1) * 8 = 24
~~~

因此实际分配 24 字节槽，其中 4 字节是尺寸向上取整产生的内部碎片。

### 16.3 初始化和按需申请生命周期

~~~mermaid

~~~

本框图说明：这是“静态池数组构造、设置槽尺寸、首次分配时延迟申请 Block、归还槽并复用，直到程序退出才整体释放 Block”的生命周期框图。

`initMemoryPool()` 只负责设置 `slotSize_`，不负责申请 Block。它必须在任何小对象分配前完成，并且应保证只初始化一次。当前源码没有使用 `std::call_once`保护该过程。

### 16.4 Block 内存布局

每个 Block 的开头保存上一个 Block 的地址，其后是对齐填充和固定大小槽：

~~~mermaid
flowchart LR
    BASE["newBlock 起始地址"]
    HEAD["Block 头<br/>next 指针"]
    PAD["对齐填充"]
    S0["Slot 0"]
    S1["Slot 1"]
    S2["Slot 2"]
    MORE["Slot ..."]
    END["Block 结束边界"]

    BASE --> HEAD --> PAD --> S0 --> S1 --> S2 --> MORE --> END
~~~

本框图说明：这是“一个 Block 从起始地址到结束边界，依次由 Block 链表头、对齐填充和多个同大小 Slot 组成”的内存布局框图。

`allocateNewBlock()` 的关键关系是：

~~~text
newBlock
  -> 开头 sizeof(Slot*) 字节保存下一个 Block 地址
  -> endofhead 指向 Block 头之后
  -> paddingsize 将地址推进到目标边界
  -> curSlot_ 指向第一个可分配槽
  -> lastSlot_ 限定最后一个完整槽的起始位置
~~~

假设 Block 为 4096 字节，Slot 为 64 字节，理论上限为 `4096 / 64 = 64` 个槽；但 Block 头和对齐填充会占用空间，所以实际槽数会少于理论值。槽越小，一个 Block 可容纳的槽越多；槽越大，可容纳的槽越少。

### 16.5 三类指针和两条链表

`MemoryPool` 内部需要同时追踪“大内存块”和“已归还小槽”：

~~~mermaid
flowchart TB
    MP["MemoryPool"]

    MP --> FB["firstBlock_<br/>Block 链表头"]
    FB --> B3["Block 3"]
    B3 --> B2["Block 2"]
    B2 --> B1["Block 1"]
    B1 --> BN["nullptr"]

    MP --> FL["freeList_<br/>已归还槽链表头"]
    FL --> F3["Block 3 中的槽 J"]
    F3 --> F2["Block 2 中的槽 G"]
    F2 --> F1["Block 1 中的槽 B"]
    F1 --> FN["nullptr"]

    MP --> CUR["curSlot_<br/>下一个从未使用槽"]
    MP --> LAST["lastSlot_<br/>当前 Block 槽边界"]
~~~

本框图说明：这是“`firstBlock_` 连接所有大内存块，`freeList_` 跨 Block 连接已分配后归还的槽，`curSlot_/lastSlot_` 管理当前 Block 中从未分配的连续槽”的双链表和边界指针框图。

`Slot` 结构在两处被复用：

~~~cpp
struct Slot
{
    Slot *next;
};
~~~

1. Block 开头被解释为 `Slot`，`next` 连接下一个 Block。
2. 已归还槽的前几个字节被解释为 `Slot`，`next` 连接下一个已归还槽。

`freeList_` 不包含从未分配过的槽。从未分配槽通过 `curSlot_` 顺序向后推进，避免创建 Block 时逐个初始化槽链表。

### 16.6 `allocate()` 分配流程

~~~mermaid
flowchart TD
    CALL["MemoryPool::allocate"] --> LOCKFREE["检查 freeList"]
    LOCKFREE --> HASFREE{"freeList 有归还槽"}
    HASFREE -- "是" --> POP["弹出链表头"]
    POP --> MOVEHEAD["freeList = freeList->next"]
    MOVEHEAD --> RETFREE["返回复用槽"]

    HASFREE -- "否" --> LOCKBLOCK["锁定 Block 分配状态"]
    LOCKBLOCK --> EXHAUST{"curSlot 为空<br/>或超过边界"}
    EXHAUST -- "是" --> NEWBLOCK["allocateNewBlock"]
    NEWBLOCK --> SETCUR["设置 curSlot 和 lastSlot"]
    EXHAUST -- "否" --> TAKE["取当前 curSlot"]
    SETCUR --> TAKE
    TAKE --> ADVANCE["curSlot 后移 slotSize 字节"]
    ADVANCE --> RETNEW["返回从未用过的槽"]
~~~

本框图说明：这是“分配时优先复用 `freeList_` 中的已归还槽；没有归还槽时从 `curSlot_` 顺序分配；当前 Block 耗尽时再申请新 Block”的分配逻辑框图。

当槽尺寸为 64 字节，并且 `sizeof(Slot) == 8` 时：

~~~cpp
curSlot_ += slotSize_ / sizeof(Slot); // 向后移动 64 / 8 个 Slot 单位
~~~

结果是地址向后移动 64 字节。为了避免将原始字节块假定为 `Slot[]`，更清晰的实现是将地址转为 `char*` 后直接增加 `slotSize_` 字节。

### 16.7 `deallocate()` 归还流程

~~~mermaid
sequenceDiagram
    participant O as 已析构对象
    participant MP as MemoryPool
    participant M as freeList 互斥锁
    participant FL as freeList

    O->>MP: deallocate(p)
    MP->>MP: p 转为 Slot 指针
    MP->>M: 加锁
    MP->>FL: slot->next = freeList
    MP->>FL: freeList = slot
    MP->>M: 离开作用域自动解锁
    Note over FL: 槽留在 Block 中<br/>等待后续复用
~~~

本框图说明：这是“`deallocate()` 将对象已析构的原始槽使用头插法加入 `freeList_`，而不是对槽地址直接调用 `free()`”的归还时序图。

槽地址只是某个 4096 字节 Block 内部的子区域，不是 `malloc()` 单独返回的地址，因此不能对单个槽调用系统 `free()`。只有 `MemoryPool` 析构时才沿 `firstBlock_` 释放完整 Block。

### 16.8 对象构造与析构

`MemoryPool::allocate()` 只返回原始内存，不会调用业务对象的构造函数。`newElement<T>()` 使用 placement new 把“取得内存”和“构造对象”连接起来：

~~~mermaid
flowchart LR
    NEW["newElement T args"] --> SIZE["sizeof T"]
    SIZE --> RAW["HashBucket::useMemory"]
    RAW --> SLOT["取得原始 Slot"]
    SLOT --> PLACE["placement new<br/>在 Slot 中构造 T"]
    PLACE --> PTR["返回 T 指针"]

    PTR --> USE["调用者使用对象"]
    USE --> DEL["deleteElement T"]
    DEL --> DTOR["p->~T<br/>执行析构"]
    DTOR --> FREE["HashBucket::freeMemory"]
    FREE --> BACK["槽返回 freeList"]
~~~

本框图说明：这是“`newElement<T>()` 从池中取得原始槽并通过 placement new 构造对象，`deleteElement<T>()` 显式析构对象后再归还槽”的对象生命周期框图。

两个阶段不能混淆：

~~~text
HashBucket::useMemory   -> 只分配原始内存
placement new           -> 在原始内存中构造 T
p->~T()                 -> 结束 T 的对象生命周期
HashBucket::freeMemory  -> 归还或系统释放原始内存
~~~

`newElement<T>()` 中的 `Args&&...` 是转发引用参数包，`std::forward<Args>(args)...` 保留每个构造参数原有的左值或右值属性。由 `newElement()` 创建的对象必须使用 `deleteElement()` 销毁，不能使用普通 `delete`。

### 16.12 当前实现的正确性风险

以下是当前两个 MemoryPool 源文件中可直接确认的问题，它们需要在将内存池用于真实对象前修复：

~~~mermaid
flowchart TB
    R["当前实现风险"]
    R --> R1["init 从 i=1 开始<br/>8 字节池未初始化"]
    R --> R2["首次 allocate<br/>未显式检查 curSlot 为空"]
    R --> R3["freeList 加锁前读取<br/>存在数据竞争"]
    R --> R4["新 Block 清空 freeList<br/>可能丢失归还槽"]
    R --> R5["malloc 失败后<br/>仍继续计算地址"]
    R --> R6["padding 公式<br/>非二次幂槽可计算错误"]
    R --> R7["lastSlot 加 1<br/>边界含义不严谨"]
    R --> R8["只按 sizeof 分池<br/>过度对齐类型不可靠"]
~~~

本框图说明：这是“当前 MemoryPool 实现在初始化、首次分配、并发链表访问、失败处理、对齐和边界计算方面的已知正确性风险”的汇总框图。

具体问题如下：

1. `initMemoryPool()` 从 `i = 1` 开始，使 `memoryPool[0]` 的 `slotSize_` 保持为 0；应从 `i = 0` 开始。
2. `allocate()` 首次进入时 `curSlot_` 和 `lastSlot_` 都为空，应显式使用 `curSlot_ == nullptr || curSlot_ > lastSlot_` 判断是否需要首个 Block。
3. `allocate()` 在获取 `mutexForFreeList_` 前读取 `freeList_`，与其他线程在 `deallocate()` 中的写入构成未同步读写。
4. `allocateNewBlock()` 不应设置 `freeList_ = nullptr`；该链表属于整个 `MemoryPool`，不属于新 Block。
5. `malloc()` 返回空指针后代码仍对 `newBlock` 做地址运算，应立即抛出 `std::bad_alloc` 或返回错误。
6. `padPointer()` 应先计算 `address % slotSize`，再计算补齐量；当前无符号减法对 24、40 等非二次幂槽尺寸不可靠。
7. `lastSlot_` 的 `+1` 将“最后合法槽起始地址”和“超界边界”混在一起，应使用明确的块结束指针进行字节边界判断。
8. `newElement()` 中如果 `T` 的构造函数抛异常，已取得槽不会自动归还。
9. `MemoryPool` 析构只释放 Block，不知道哪些槽中仍有活跃对象；调用者必须先完成对象析构。
10. 注释中的“4096 字节等于页对齐”不准确；`malloc(4096)` 表示分配长度为 4096，不保证返回地址按 4096 字节页边界对齐。

因此，本章前面的分配和归还框图表达的是该内存池的设计意图。当前代码需先修复上述问题，再将它接入关键运行路径或用于多线程高并发分配。

## 17. io_uring 与 liburing

`io_uring` 是 Linux 内核提供的异步 I/O 接口，`liburing` 是对这套内核接口的用户态封装库。本项目通过 `liburing` 创建 ring、准备 SQE、读取 CQE，不需要自己直接调用 `io_uring_setup` 和 `io_uring_enter` 等底层系统调用。

### 17.1 `struct io_uring_params`

`io_uring_params` 是创建 `io_uring` 时传给内核的参数结构。它同时具有两种职责：

1. **输入参数**：用户态在初始化前填写 `flags`、`sq_thread_idle` 等字段，告诉内核希望以什么方式创建 ring。
2. **输出参数**：创建成功后，内核回填实际的 SQ/CQ 队列大小、支持的特性以及各区域的内存偏移信息。`liburing` 再根据这些信息完成 ring 的内存映射和用户态结构初始化。

Linux UAPI 中该结构的核心字段可简化理解为：

~~~cpp
struct io_uring_params
{
    __u32 sq_entries;       // 内核回填：SQ 实际容量
    __u32 cq_entries;       // 内核回填：CQ 实际容量
    __u32 flags;            // 用户填写：创建 ring 时的 IORING_SETUP_* 选项
    __u32 sq_thread_cpu;    // 可选输入：SQPOLL 线程绑定的 CPU
    __u32 sq_thread_idle;   // 可选输入：SQPOLL 空闲多少毫秒后休眠
    __u32 features;         // 内核回填：IORING_FEAT_* 能力集
    __u32 wq_fd;            // 可选输入：共享另一个 ring 的 io-wq
    struct io_sqring_offsets sq_off; // 内核回填：SQ 映射布局
    struct io_cqring_offsets cq_off; // 内核回填：CQ 映射布局
};
~~~

> 上面为便于理解的精简展示，完整结构还包含保留字段。项目应始终使用系统 `<linux/io_uring.h>` 和 `liburing` 提供的定义，不要自己重新定义该结构。

#### 为什么必须先清零

本项目中的初始化代码是：

~~~cpp
struct io_uring_params params;
memset(&params, 0, sizeof(params));

if (options_.sqpoll)
{
    params.flags = IORING_SETUP_SQPOLL;
    params.sq_thread_idle = options_.sqpollIdleMs;
}

int ret = io_uring_queue_init_params(
    static_cast<unsigned int>(options_.ringEntries),
    &ring_,
    &params);
~~~

`params` 中没有主动设置的字段必须为 `0`。如果不清零，栈上的随机值可能被内核误解为未知标志或非法参数，使 ring 创建失败。更现代的 C++ 写法可以直接使用：

~~~cpp
struct io_uring_params params{};
~~~

`io_uring_queue_init_params()` 的三个参数分别是：

| 参数 | 本项目传入值 | 作用 |
|---|---|---|
| `entries` | `options_.ringEntries` | 请求的 SQ 队列深度 |
| `ring` | `&ring_` | 初始化 `EventLoop` 拥有的 `struct io_uring` |
| `params` | `&params` | 传入创建选项，并接收内核回填结果 |

`entries` 是向内核提出的队列深度请求，不应将它理解为“最多只能处理这么多个连接”。它限制的是同一时刻 ring 中可容纳的提交项数，而不是服务器连接总数。

~~~mermaid

    PARAMS[io_uring_params<br/>先全部清零]

    SETUP[Linux io_uring_setup]
    KERNEL[Linux 内核]
    RING[EventLoop::ring_]
    OUTPUT[内核回填<br/>sq_entries / cq_entries / features / offsets]

~~~

本框图说明：这是“`EventLoop::Options` 如何转换为 `io_uring_params`，再由 `liburing` 调用内核并初始化 `EventLoop::ring_`”的流程图。

### 17.2 SQPOLL 是什么

SQPOLL 是 **Submission Queue Polling** 的缩写。启用 `IORING_SETUP_SQPOLL` 后，内核为该 ring 维护 SQ 轮询线程，在活跃期间主动检查提交队列。用户线程把 SQE 写入 SQ 并更新队尾后，轮询线程就可以发现并消费请求，活跃期间通常可避免每批请求都通过 `io_uring_enter` 进入内核。

没有启用 SQPOLL 时，用户态准备好 SQE 之后，一般需要由 `io_uring_submit()` 触发 `io_uring_enter`，显式通知内核消费 SQ。

#### SQPOLL 不等于“永远零系统调用”

`sq_thread_idle` 指定 SQ 轮询线程在连续空闲多少毫秒后进入休眠。休眠时，内核会设置 `IORING_SQ_NEED_WAKEUP`。之后用户态再提交新 SQE 时，`liburing` 需要通过系统调用并携带 `IORING_ENTER_SQ_WAKEUP` 来唤醒它。因此更准确的表述是：

> SQPOLL 可在轮询线程活跃时减少提交路径上的系统调用，但不保证所有情况下都没有系统调用。

SQPOLL 也不是业务工作线程：它主要负责发现和提交 SQ 中的 I/O 请求，不会执行 `httpPingPongTask()`、`connectionCallback_` 或 CQE 处理逻辑。CQE 仍由项目的 `EventLoop` 线程取出并分发。

~~~mermaid
sequenceDiagram
    participant EL as EventLoop 线程
    participant SQ as Submission Queue
    participant SP as 内核 SQPOLL 线程
    participant IO as 内核 I/O 子系统
    participant CQ as Completion Queue

    EL->>SQ: 写入 SQE 并更新 SQ tail
    alt SQPOLL 线程正在轮询
        SP->>SQ: 发现并消费 SQE
    else 空闲超时，SQPOLL 已休眠
        EL->>SP: io_uring_enter + SQ_WAKEUP
        SP->>SQ: 被唤醒后消费 SQE
    end
    SP->>IO: 发起 I/O 操作
    IO->>CQ: I/O 完成，生成 CQE
    EL->>CQ: io_uring_wait_cqe / 批量遍历
    EL->>EL: handleCompletionEvent
~~~

本框图说明：这是“SQPOLL 活跃时直接消费 SQE，休眠后需要用户态唤醒，最终由 EventLoop 处理 CQE”的时序图。

#### SQPOLL 的收益与代价

| 方面 | 影响 |
|---|---|
| 提交延迟 | 轮询线程活跃时，可减少显式进入内核的次数 |
| 高频小 I/O | 每次 I/O 的提交成本占比高，更可能受益 |
| CPU 占用 | 活跃轮询会占用 CPU 时间，设置太长会增加空载消耗 |
| 线程数 | 本项目每个 EventLoop 拥有自己的 ring；每个 ring 启用 SQPOLL 都会增加内核轮询资源 |
| 低负载场景 | 轮询带来的 CPU 代价可能大于减少系统调用的收益 |
| 运行环境 | 受 Linux 内核版本、权限、锁定内存限制和容器配置影响，初始化可能失败 |

#### 本项目中的实际配置

`EventLoop::Options` 中的编译期默认值是：

~~~cpp
bool sqpoll = true;
unsigned int sqpollIdleMs = 50;
~~~

但当前 `config/ucp.conf` 明确配置为：

~~~ini
[event_loop]
sqpoll = false
sqpoll_idle_ms = 50
~~~

`src/test.cpp` 先用配置文件覆盖 `EventLoop::Options`，然后使用同一份 `loopOptions` 创建主 `EventLoop` 并配置 Worker `EventLoop`。因此，按当前默认配置启动 `src/test.cpp` 服务时，主 ring 和 Worker ring **都不启用 SQPOLL**；只有将配置改为 `true` 时，构造函数才会设置 `IORING_SETUP_SQPOLL`。

当 SQPOLL 关闭时，`sq_thread_idle` 不参与工作；它只有在 `IORING_SETUP_SQPOLL` 已设置时才有意义。
