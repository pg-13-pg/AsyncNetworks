# UCP 项目深度阅读指南

本文面向希望系统理解本项目的读者。建议先把它当作一个“实验型 io_uring 网络框架”来学习，再把推荐服务当作业务集成示例阅读。不要一开始从所有文件逐行通读，先建立运行时主线，再深入每个机制。

## 1. 先明确项目边界

项目可以分成三层：

```text
核心网络框架
  EventLoop / io_uring / TcpServer / TcpConnection / Acceptor
  协程读写 / Buffer / Socket / 线程池 / 任务队列

基础设施
  Logger / Config / MemoryPool / HTTP 编解码 / RPC 编解码

示例与测试
  src/test.cpp
  client/test_client.cpp
  bench/echo_bench.cpp
  recommend/
```

核心框架约 4,640 行物理代码、约 3,104 行有效代码。`recommend/` 是独立业务 Demo，不是 `proactor_test` 的默认业务路径。

## 2. 第一阶段：建立可重复的构建环境

项目要求 Linux、C++20、liburing、fmt、CMake 和 pkg-config。首次构建建议使用显式的 source/build 目录：

```bash
sudo apt update
sudo apt install -y build-essential cmake pkg-config liburing-dev libfmt-dev

cd ~/uring_coroutine_proactor
cmake -S . -B build
cmake --build build -j"$(nproc)"
```

主要产物：

```text
lib/libproactor.a
lib/libproactor.so
bin/proactor_test
bin/recommend_server
client/test_client
recommend/recommend_client
```

先确认编译成功，再开始源码阅读。编译错误本身也是理解“头文件自包含、库依赖和目标链接关系”的机会。

## 3. 第二阶段：先读默认服务器启动链

按以下顺序阅读：

1. `src/test.cpp`
2. `config/ucp.conf`
3. `include/TcpServer.hpp` 和 `src/TcpServer.cpp`
4. `include/Acceptor.hpp` 和 `src/Acceptor.cpp`
5. `include/EventLoop.hpp` 和 `src/EventLoop.cpp`
6. `include/TcpConnection.hpp` 和 `src/TcpConnection.cpp`

启动链可以概括为：

```text
main
  -> 加载 Config
  -> 初始化 Logger
  -> 初始化 MemoryPool
  -> 创建主 EventLoop
  -> 初始化 registered buffers
  -> 创建 TcpServer
  -> 创建 Acceptor
  -> 创建 EventLoopThreadPool
  -> listen
  -> 主 EventLoop::loop()
```

重点跟踪 `src/test.cpp` 中这些动作：

- 配置如何映射到 `EventLoop::Options`；
- `server.setThreadNum()` 如何决定工作线程数；
- `server.setEventLoopOptions()` 如何把 io_uring 配置传给子线程；
- `server.start()` 为什么只在主线程监听；
- `loop.loop()` 为什么最后只进入主 EventLoop。

当前配置文件中的端口和线程数以实际文件为准，不要直接套用 README 中的历史数字。服务端监听 `0.0.0.0` 时，客户端本机测试优先使用 `127.0.0.1`。

## 4. 第三阶段：理解 One Ring Per Thread

本项目的核心模型是：

```text
主线程 EventLoop
  负责监听 socket 和 accept

每个工作线程
  拥有自己的 EventLoop
  拥有自己的 io_uring ring
  处理分配到该线程的 TcpConnection
```

阅读重点：

- `EventLoopThread::threadFunc()`：子线程如何创建栈上 EventLoop；
- `EventLoopThreadPool::start()`：如何保存子线程 EventLoop 指针；
- `EventLoopThreadPool::getNextLoop()`：连接如何轮询分配；
- `TcpServer::newConnection()`：连接对象在哪个线程建立；
- `TcpServer::removeConnection()`：关闭回调如何回到主线程，再回到连接所属线程。

需要特别理解两个线程边界：

```text
主 EventLoop -> 接收新连接、维护 connections_
子 EventLoop -> 连接上的读写、协程恢复、连接销毁
```

阅读时画出每个函数所在的线程。很多并发正确性问题，只有标出线程归属后才容易发现。

## 5. 第四阶段：深入 io_uring 事件循环

重点阅读 `src/EventLoop.cpp` 的以下逻辑：

### 初始化

- `io_uring_queue_init_params()`；
- `IORING_SETUP_SQPOLL` 和 `sq_thread_idle`；
- `eventfd` 唤醒机制；
- 第一个 wakeup read 请求。

### 主循环

理解每一轮的顺序：

```text
准备 SQE
  -> io_uring_submit
  -> io_uring_wait_cqe
  -> handleCompletionEvent
  -> 执行 handler 或恢复 coroutine
```

### Completion 分发

阅读 `IoContext` 和 `EventLoop::handleCompletionEvent()`，回答：

- `user_data` 指向什么对象；
- 如何区分 Read、Write、Timeout、Accept、Wakeup；
- `cqe->res` 的正数、0、负数分别如何处理；
- 协程句柄何时保存、何时恢复、何时清空；
- 同一个连接上的读请求、超时请求和关闭请求如何避免重复处理。

### 固定缓冲区

阅读：

- `EventLoop::initRegisteredBuffers()`；
- `getRegisteredBufferIndex()`；
- `returnRegisteredBuffer()`；
- `TcpConnection::submitReadRequest()`；
- `AsyncReadAwaitable::await_resume()`。

画出缓冲区生命周期：

```text
初始化分配
  -> io_uring_register_buffers
  -> 获取空闲索引
  -> read_fixed 使用
  -> 协程恢复后读取数据
  -> releaseCurReadBuffer
  -> 索引归还空闲栈
```

注意：固定缓冲区注册失败时当前实现只记录错误，后续读路径仍可能继续运行。阅读时要思考这种错误是否应该变成启动失败或降级到普通 read。

## 6. 第五阶段：理解 C++20 协程读写

阅读顺序：

1. `include/CoroutineTask.hpp`
2. `include/AsyncRead.hpp`、`src/AsyncRead.cpp`
3. `include/AsyncWrite.hpp`、`src/AsyncWrite.cpp`
4. `TcpConnection::asyncRead()`、`asyncSend()`
5. `src/test.cpp` 中的 `httpPingPongTask()`

以一次读操作为例，必须能解释以下完整链路：

```text
co_await conn->asyncRead(4096)
  -> await_ready()
  -> await_suspend(handle)
  -> 保存 coroutine_handle
  -> 获取 registered buffer
  -> 准备 read_fixed SQE
  -> 准备 link timeout SQE
  -> EventLoop 提交 SQE
  -> CQE 完成
  -> 写入 IoContext::result_
  -> resume coroutine
  -> await_resume() 返回字节数
```

写操作需要另外关注：

- `outputBuffer_` 的读写索引；
- 短写是否会继续提交；
- `asyncSend()` 返回的字节数如何处理；
- 连接处于 `kDisconnecting` 时是否允许继续写；
- 背压策略 `kDiscard`、`kCloseConnection`、`kBlock`、`kPass` 的实际调用路径。

## 7. 第六阶段：理解连接生命周期

建议画出状态机：

```text
kDisconnected
      |
      v
kConnecting -> kConnected -> kDisconnecting -> kDisconnected
```

重点函数：

- `connectEstablished()`；
- `forceClose()`；
- `handleClose()`；
- `connectDestroyed()`；
- `reset()`；
- `shutdown()` 和 `maybeShutdownWrite()`。

必须回答：

- 谁持有 `TcpConnection` 的 `shared_ptr`；
- 协程是否会延长连接生命周期；
- close callback 是否可能重复调用；
- fd 在哪个函数真正关闭；
- io_uring 中仍然挂起的请求如何结束；
- registered buffer 在成功、失败、超时和异常关闭时是否都能归还。

建议用已有客户端测试逐项验证：

```bash
./client/test_client 1 127.0.0.1 6666
./client/test_client 2 127.0.0.1 6666
./client/test_client 3 127.0.0.1 6666
./client/test_client 4 127.0.0.1 6666
./client/test_client 5 127.0.0.1 6666
```

服务端日志中的典型返回值：

```text
-125  ECANCELED   链接超时被正常读操作取消
-62   ETIME      真正发生读超时
-104  ECONNRESET  对端发送 RST
 0                对端正常关闭
```

## 8. 第七阶段：阅读 HTTP 和 RPC 编解码

HTTP 有两套实现，不能混为一谈：

### `src/test.cpp` 内置解析器

`proactor_test` 使用自己的 `HttpRequest`，直接在测试入口文件中解析 HTTP。它用于简单 Ping-Pong 和推荐服务之外的基础示例。

### `HttpCodec`

`include/codec/HttpCodec.hpp` 和 `codec/HttpCodec.cpp` 提供独立编解码器，但默认 `proactor_test` 没有用它完成请求解析。阅读时要确认“实现存在”和“运行路径实际调用”是两件事。

### `RpcCodec`

阅读 `codec/RpcCodec.cpp` 时重点确认协议布局：

```text
4 bytes body length
4 bytes type
8 bytes request id
N bytes payload
```

然后阅读 `codec/RpcCodec使用示例.md`，自己写一个最小 encode/decode 测试，验证：

- 半包不会错误消费 Buffer；
- 超过最大长度会返回错误；
- 64 位 ID 在大小端转换后保持一致；
- 连续两个 RPC 包可以依次解析。

## 9. 第八阶段：基础设施

### Buffer

阅读：

- `include/Buffer.hpp`；
- `src/Buffer.cpp`。

重点理解 `readIndex_`、`writeIndex_`、可读区、可写区、扩容和头部预留空间。然后检查 `retrieve()`、`ensureWritableBytes()`、`makeSpace()` 是否满足粘包/拆包场景。

### LockFreeQueue

阅读 `include/LockFreeQueue.hpp` 时先明确它的算法假设：

- 环形数组容量必须是 2 的幂；
- 使用 sequence 处理生产者/消费者位置；
- `enqueue` 和 `dequeue` 的内存序；
- `size()` 只是并发近似值；
- `std::function` 移动和异常安全如何影响队列。

### Logger

阅读 `include/Logger.hpp` 和 `log/Logger.cpp`，重点观察：

- 同步/异步模式；
- 日志队列和后台线程；
- 文件轮转；
- 日志等级判断是否在格式化前完成；
- 高并发下每请求日志对性能的影响。

压测时不要只看 RPS，也要比较日志文件增长和 CPU：

```bash
du -h logs/server.log
pidstat -u -d -p "$(pgrep -xo proactor_test)" 1
```

### MemoryPool

阅读 `include/MemoryPool.hpp` 和 `memory/MemoryPool.cpp`，确认它实际服务哪些对象。不要因为类名叫 MemoryPool，就假设所有 `TcpConnection`、字符串和协程帧都使用了它。

## 10. 第九阶段：性能实验方法

同机压测同时消耗服务端和客户端 CPU，因此只能作为初步实验。推荐先固定参数：

```bash
wrk -t4 -c1000 -d60s --timeout 5s --latency \
    http://127.0.0.1:6666
```

用 5 个终端观察：

```bash
# 服务端
sudo sh -c 'ulimit -n 100000; ulimit -l unlimited; exec ./bin/proactor_test config/ucp.conf'

# 服务端总量
SERVER_PID=$(pgrep -xo proactor_test)
pidstat -u -p "$SERVER_PID" 1

# 服务端线程
pidstat -u -t -p "$SERVER_PID" 1

# wrk 线程
WRK_PID=$(pgrep -nx wrk)
pidstat -u -t -p "$WRK_PID" 1

# 整机
mpstat -P ALL 1
```

先比较 `wrk -t1/-t2/-t4/-t6`，再比较服务端 `thread_num=6/8/10/12`。每次只改变一个变量。

性能数据至少记录：

- Requests/sec；
- Transfer/sec；
- 平均延迟和 P99；
- 连接错误、读错误、写错误和超时；
- 服务端总 CPU 和线程 CPU；
- wrk 总 CPU 和线程 CPU；
- 日志增长量；
- 进程 RSS 和 FD 数量。

当前项目的一个重要实验结论是：如果 `wrk` 的 4 个线程都接近 100%，同机测试得到的 RPS 不能直接当作服务端极限。

## 11. 第十阶段：单独阅读 recommend Demo

推荐模块的阅读顺序：

1. `recommend/RecommendProtocol.hpp`
2. `recommend/FeatureStore.hpp`
3. `recommend/RankingModel.hpp`
4. `recommend/RecommendationHandler.hpp`
5. `recommend/recommend_server.cpp`
6. `recommend/recommend_client.cpp`

业务链路：

```text
POST /recommend
  -> 手写 HTTP 解析
  -> 手写 JSON 字段解析
  -> 固定生成 100 个候选
  -> 读取/生成用户和物品特征
  -> 计算余弦相似度和融合分数
  -> 排序取 Top-K
  -> JSON 序列化
```

它是演示代码，不是真实生产推荐系统。阅读时重点识别以下限制：

- LRU 使用 `shared_ptr` 双向链接，存在循环引用风险；
- FeatureStore 注明线程不安全，但服务实例被多个 worker 共享；
- trace ID 的静态随机数生成器存在并发访问风险；
- 响应错误状态目前仍可能返回 HTTP 200；
- 推荐客户端默认端口与当前配置端口可能不一致；
- 客户端一次 `send()`/`recv()` 不能保证完整 TCP 消息；
- 召回、特征和模型都是模拟实现。

构建成功后，停止 `proactor_test`，再启动推荐服务。若 `config/ucp.conf` 使用 6666 端口，客户端显式指定端口：

```bash
sudo sh -c 'ulimit -n 100000; ulimit -l unlimited; exec ./bin/recommend_server config/ucp.conf'

./recommend/recommend_client -s 127.0.0.1 -p 6666 -n 10 -t 1
```

也可以用 curl 单独验证接口：

```bash
curl -i http://127.0.0.1:6666/health
curl -i http://127.0.0.1:6666/stats
curl -i -X POST http://127.0.0.1:6666/recommend \
  -H 'Content-Type: application/json' \
  -d '{"user_id":12345,"count":10,"scene":"homepage"}'
```

## 12. 代码审查清单

深度学习时，不要只问“能不能跑”，还要逐项问：

### 正确性

- 所有 partial read/write 是否处理；
- 所有协议长度是否有上限；
- 所有负数 CQE 是否正确转换 errno；
- timeout 和 read 的两个 CQE 是否可能重复关闭连接；
- 协程 frame 和 `shared_ptr` 是否互相延长生命周期；
- Buffer 索引在所有退出路径是否归还。

### 并发

- 哪些数据只在 EventLoop 所属线程访问；
- 哪些数据跨线程访问；
- `connections_` 是否只由主线程操作；
- pending queue 的生产者/消费者模型是否满足算法假设；
- 日志、缓存和统计计数是否线程安全。

### 资源

- fd 是否一定关闭；
- io_uring ring 是否一定退出；
- registered buffers 是否一定 unregister 和 free；
- 日志线程是否在 shutdown 前完成 flush；
- 异常路径是否释放协程和缓存对象。

### 性能

- 是否每请求创建大量 `std::string`；
- 是否每次读操作都绑定 timeout；
- 是否存在每请求 INFO 日志；
- 是否发生不必要的数据拷贝；
- 测试端是否先成为 CPU 瓶颈；
- WSL 的虚拟化调度是否影响结论。

## 13. 推荐的学习节奏

### 第 1 天：能运行

- 完成构建；
- 启动 `proactor_test`；
- 用 `test_client 1/2/3/4/5` 验证基础行为；
- 读懂 `src/test.cpp` 的 HTTP Ping-Pong 协程。

### 第 2 天：能画出框架

- 画出主 EventLoop、工作 EventLoop 和连接对象关系；
- 画出 accept、read、timeout、write、close 的 CQE 流程；
- 解释每个 `IoContext` 的生命周期。

### 第 3 天：能解释内存和并发

- 读懂 registered buffer 池；
- 读懂 LockFreeQueue 的 sequence 算法；
- 用 `/proc`、`pidstat`、`ss` 检查 fd、线程和内存；
- 找出至少三个潜在并发风险。

### 第 4 天：能做性能实验

- 固定 `wrk` 参数重复测试；
- 比较 wrk 线程数和服务端 worker 数；
- 区分用户态、内核态、调度等待和真实 I/O；
- 记录并解释 RPS、延迟和错误。

### 第 5 天：能扩展业务

- 阅读 `HttpCodec` 和 `RpcCodec`；
- 写一个独立 RPC encode/decode 小测试；
- 阅读 `recommend/`，理解网络层与业务层的边界；
- 尝试为推荐服务补充真实 HTTP 状态码、并发安全缓存和完整收发循环。

## 14. 最终学习目标

完成本指南后，应能独立回答：

1. 一个连接从 accept 到销毁经过哪些线程和状态；
2. 一个 `co_await asyncRead()` 如何映射到 SQE、CQE 和协程恢复；
3. 固定缓冲区为什么需要 `memlock`，失败时会发生什么；
4. 超时 CQE 和读 CQE 如何协作；
5. 线程池、pending queue 和 eventfd 如何完成跨线程调度；
6. Buffer 如何处理半包、粘包和连续请求；
7. 为什么同机 `wrk` 的 RPS 不能直接代表服务端极限；
8. 哪些代码是核心框架，哪些代码只是业务 Demo；
9. 当前实现距离生产级网络库还缺少哪些保证。

建议每读完一个模块，就写一个小实验或最小测试，而不是只看注释。这个项目最适合通过“源码调用链 + 内核行为 + 可观测数据”三者互相验证来学习。
