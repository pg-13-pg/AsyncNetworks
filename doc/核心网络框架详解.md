# 核心网络框架详解

本文面向希望深入学习本项目的读者，重点解释核心网络框架的设计、线程模型和一次 I/O 请求的完整生命周期。文档以当前源码为准，不替代代码本身；阅读时建议同时打开对应的头文件和实现文件。

## 1. 框架定位

本项目是一个 Linux TCP 网络框架，核心技术组合是：

- Linux `io_uring`：提交异步 I/O 请求，并从完成队列（CQ）获得结果。
- C++20 coroutine：把异步读写包装成 `co_await`，让业务代码保持顺序化写法。
- Proactor 模型：应用线程提交 I/O，内核完成 I/O 后通知事件循环，事件循环再恢复协程或调用回调。
- 多 EventLoop：一个主 EventLoop 负责监听和接收连接，多个工作 EventLoop 负责已建立连接的数据读写。

它不是传统的 `epoll + 非阻塞 read/write` 框架。`epoll` 通常通知“现在可以读写”，应用还要自己调用 `read` 或 `write`；本项目直接把读写请求交给 `io_uring`，完成后从 CQE 中取得字节数或错误码。

## 2. 从入口到业务的层次

默认测试入口位于 **`src/test.cpp`**。使用者通常只需要创建 `EventLoop` 和 `TcpServer`，设置线程数、超时和连接回调，然后调用 `start()`。

```text
src/test.cpp
    |
    v
TcpServer
    |-- Acceptor                 主 EventLoop 上监听端口、接收连接
    |-- EventLoopThreadPool      创建工作线程和工作 EventLoop
    |-- TcpConnection             每个 TCP 连接的状态、缓冲区和协程
              |
              |-- AsyncReadAwaitable
              |-- AsyncWriteAwaitable
              |-- IoContext         绑定 io_uring 的 user_data
              |-- Buffer             输入/输出缓冲区
              |-- Socket             fd 和地址封装
              v
          EventLoop
              |-- io_uring SQ/CQ
              |-- eventfd 唤醒
              |-- LockFreeQueue 跨线程任务
```

核心源码目录可按以下边界理解：

| 模块 | 主要文件 | 责任 |
| --- | --- | --- |
| 事件循环 | **`include/EventLoop.hpp`**, **`src/EventLoop.cpp`** | 初始化 ring、提交和收割 CQE、恢复协程、执行跨线程任务 |
| 服务器 | **`include/TcpServer.hpp`**, **`src/TcpServer.cpp`** | 组织监听器、线程池和活动连接，管理连接生命周期 |
| 接收连接 | **`include/Acceptor.hpp`**, **`src/Acceptor.cpp`** | 创建监听 socket，提交异步 accept，批量取尽连接队列 |
| TCP 连接 | **`include/TcpConnection.hpp`**, **`src/TcpConnection.cpp`** | 读写请求、状态转换、输入输出缓冲区和关闭流程 |
| 工作线程 | **`include/EventLoopThread.hpp`**, **`src/EventLoopThread.cpp`**, **`src/EventLoopThreadPool.cpp`** | 每个线程运行一个独立 EventLoop |
| 协程 I/O | **`include/AsyncRead.hpp`**, **`include/AsyncWrite.hpp`** | 将 I/O 请求封装为 awaitable |
| 请求上下文 | **`include/IoContext.hpp`** | 保存操作类型、fd、buffer 索引、协程句柄和结果 |
| 数据缓冲 | **`include/Buffer.hpp`**, **`src/Buffer.cpp`** | 管理可读区、可写区和数据移动 |
| 基础设施 | `Socket`, `InetAddress`, `Logger`, `MemoryPool`, `LockFreeQueue` | fd、地址、日志、对象分配和跨线程任务 |

## 3. 线程模型

### 3.1 主线程

构造 `TcpServer` 时，传入的 `EventLoop` 是主循环。`TcpServer::start()` 完成两件事：

1. 启动 `EventLoopThreadPool`，创建配置数量的工作线程。
2. 在主 EventLoop 中让 `Acceptor` 执行 `listen()` 并提交第一个 accept 请求。

主线程通常只处理监听 socket 和新连接分发，不直接处理已建立连接的读写。

### 3.2 工作线程

每个 `EventLoopThread` 在线程函数中创建一个 EventLoop，并把指针交给线程池保存。每个 EventLoop 拥有独立的 `io_uring` ring、eventfd、任务队列和注册缓冲区池。

新连接到达后，`EventLoopThreadPool::getNextLoop()` 以轮询方式选择工作 EventLoop。连接对象随后通过 `ioLoop->runInLoop(...)` 在目标线程中执行 `connectEstablished()`，从此该连接的 I/O 请求都提交到这个 ring。

这种设计的关键约束是：

- 一个 `TcpConnection` 的所有 I/O 状态应由同一个 EventLoop 线程操作。
- 主线程可以通过 `queueInLoop()` 请求工作线程执行任务。
- 连接从主线程的 `connections_` 中移除后，还要在所属工作线程执行 `connectDestroyed()`，避免跨线程销毁正在使用的对象。

### 3.3 无工作线程的情况

当线程数为 0 时，线程池返回主 EventLoop，服务器退化为单线程模式。这有利于调试，也能排除跨线程调度对性能测试的影响。

## 4. EventLoop 的组成

`EventLoop` 是框架的核心调度器，主要成员包括：

- `struct io_uring ring_`：提交队列 SQ 和完成队列 CQ 的 liburing 封装。
- `wakeupFd_`：Linux `eventfd`，用于跨线程唤醒事件循环。
- `wakeupContext_`：专门对应 eventfd 读请求的 `IoContext`。
- `pendingFunctors_`：跨线程投递的 `std::function<void()>` 无锁队列。
- `registeredBuffersPool`：页对齐分配的固定缓冲区。
- `freeBufferIndices_`：单线程访问的空闲缓冲区索引栈。

### 4.1 初始化 ring

构造函数会规范化 `EventLoop::Options`，然后调用 `io_uring_queue_init_params()`。默认选项包括：

```cpp
ringEntries = 32768;
sqpoll = true;
sqpollIdleMs = 50;
registeredBuffersCount = 16384;
registeredBuffersSize = 4096;
pendingQueueCapacity = 65536;
```

启用 `IORING_SETUP_SQPOLL` 后，内核会维护 SQ poller 线程，在 ring 有新请求时减少显式 `io_uring_enter` 的系统调用开销。该模式通常需要更高的锁定内存和内核资源，不能只看用户态 `ulimit -n`。

### 4.2 主循环

`EventLoop::loop()` 的逻辑可以简化为：

```text
while (!quit_):
    如果 SQ 有待提交 SQE，调用 io_uring_submit()
    io_uring_wait_cqe() 等待至少一个 CQE
    遍历本轮所有 CQE
        handleCompletionEvent(cqe)
    推进 CQ 头指针
    执行 pendingFunctors_
```

批量处理 CQE 可以减少每个完成事件一次函数调用和队列推进的开销。提交动作统一放在 EventLoop 中，`Acceptor`、`TcpConnection` 和 awaitable 只负责填充 SQE。

### 4.3 CQE 分发

提交 SQE 时，框架通过 `io_uring_sqe_set_data(sqe, context)` 把 `IoContext*` 放到 `user_data`。CQE 到达后：

1. 取出 `IoContext*`。
2. 保存 `cqe->res` 到 `ctx->result_`。
3. 如果存在 `coro_handle`，恢复协程。
4. 否则调用传统 `handler`。

`cqe->res` 对读写成功时是字节数，对 accept 成功时是新连接 fd，对失败时是负的 errno，例如 `-ECANCELED`、`-ETIME`、`-ENOMEM`。

连接在 CQE 到达前可能已经销毁，因此 `IoContext` 中使用 `std::weak_ptr<TcpConnection>`。处理 CQE 前会检查关联连接是否仍然存活；连接已销毁时忽略迟到的 CQE，避免访问悬空对象。

## 5. Acceptor：从监听到新连接

`Acceptor` 属于主 Proactor 线程：


1. 创建 `SOCK_NONBLOCK | SOCK_CLOEXEC` 的监听 socket。
2. 设置 `SO_REUSEADDR` 和 `SO_REUSEPORT`。
3. `bind()`、`listen()`。
4. 使用 `io_uring_prep_accept()` 提交异步 accept。

accept 完成后，`acceptContext_.handler` 调用 `Acceptor::handleRead(res)`。当 `res >= 0` 时，它就是新连接 fd，随后构造对端地址并调用 `TcpServer::newConnection()`。

本实现还有一个重要优化：处理第一个 io_uring accept 后，继续用非阻塞 `accept4()` 循环把 backlog 中已经排队的连接一次性取尽，直到 `EAGAIN`。这样可以减少连接风暴下的 CQE 和调度次数。循环结束后，只要监听仍然有效，就再次提交一个 accept 请求。

## 6. TcpServer：连接分发和所有权

`TcpServer::newConnection()` 的主要步骤如下：

```text
accept 返回 connfd
    |
    +--> threadPool.getNextLoop() 选择工作 EventLoop
    +--> 创建 shared_ptr<TcpConnection>
    +--> 设置连接回调和关闭回调
    +--> 设置读超时
    +--> 放入 connections_ 活动连接表
    +--> ioLoop->runInLoop(connectEstablished)
```

`connections_` 位于主线程，用连接名称作为 key。主线程保留一个 `shared_ptr`，保证连接在关闭流程完成前不会过早析构；连接本身又通过 `enable_shared_from_this` 在异步回调中取得安全引用。

断开流程反向进行：

1. 工作线程发现 EOF、错误或超时，调用 `TcpConnection::handleClose()`。
2. `closeCallback_` 将连接交给 `TcpServer::removeConnection()`。
3. 主线程从 `connections_` 删除连接。
4. 主线程把 `connectDestroyed()` 投递回原工作 EventLoop。
5. 工作线程取消/清理剩余状态，最终关闭 socket 并释放连接对象。

## 7. TcpConnection 的状态机

连接状态定义在 `TcpConnection.hpp`：

```text
kDisconnected  未连接或已完全断开
      |
      v
kConnecting     已创建对象，正在建立连接上下文
      |
      v
kConnected      正常读写
      |
      v
kDisconnecting  正在关闭，允许根据策略完成剩余读写
      |
      v
kDisconnected
```

`connectEstablished()` 在所属 EventLoop 线程执行，通常会把状态切换为 `kConnected`，触发连接回调并开始第一次异步读。

`checkConnected()` 同时接受 `kConnected` 和 `kDisconnecting`。这样做允许半关闭阶段继续发送剩余数据或读取最后的数据；但已经是 `kDisconnected` 时，不应再提交新的 I/O。

常用关闭操作的区别：

- `shutdown()`：发送 FIN，半关闭写端，适合优雅关闭。
- `forceClose()`：直接触发强制关闭流程，适合超时、协议错误或服务退出。
- `handleClose()`：处理底层读到 EOF 或错误后的统一关闭入口。
- `connectDestroyed()`：在正确的 EventLoop 线程完成最终销毁。

## 8. 协程和 awaitable

### 8.1 awaitable 的职责

`AsyncReadAwaitable` 和 `AsyncWriteAwaitable` 只保存一次操作所需的参数：连接指针、长度、用户缓冲区或注册缓冲区信息、文件描述符等。它们实现三个协程接口：

```cpp
bool await_ready() const noexcept;
void await_suspend(std::coroutine_handle<> handle) noexcept;
int await_resume() const noexcept;
```

典型业务代码可以写成：

```cpp
int n = co_await conn->asyncRead(4096);
if (n <= 0) {
    co_return;
}
co_await conn->asyncWrite();
```

### 8.2 一次 `co_await asyncRead()`

完整过程如下：

1. `await_ready()` 返回 `false`，协程需要异步等待。
2. `await_suspend(handle)` 在连接所属 EventLoop 线程创建或填充 `IoContext`。
3. 根据是否使用注册缓冲区，准备 `IORING_OP_READ_FIXED` 或普通 `IORING_OP_READ`。
4. 把 `handle` 保存到 `IoContext::coro_handle`。
5. 通过 `io_uring_sqe_set_data()` 绑定上下文。
6. 协程挂起，当前线程返回 EventLoop 主循环。
7. 内核完成读操作，产生 CQE。
8. `handleCompletionEvent()` 把结果写入 `result_` 并 `resume()` 协程。
9. `await_resume()` 返回保存的结果，业务代码从 `co_await` 下一行继续执行。

这里的“恢复协程”不是新建线程，也不是忙等；协程帧保存了局部变量和恢复点，线程只在 CQE 到达后继续运行它。

### 8.3 IoContext 的生命周期

`IoContext` 是 SQE 的 user_data，不能在 CQE 到达前失效。连接对象中通常保存读写上下文，因此要特别注意：

- 不能在 I/O 未完成时释放包含 `IoContext` 的连接对象。
- 不能复用同一个上下文覆盖仍在飞行中的请求。
- 连接关闭时要允许迟到 CQE 被识别并安全忽略。

awaitable 本身还重载了 `new/delete`，使用 `HashBucket` 内存池降低高频小对象分配成本。

## 9. 异步读、固定缓冲区与超时

### 9.1 注册缓冲区池

`EventLoop::initRegisteredBuffers()` 通过 `posix_memalign()` 分配页对齐内存，组成 `registeredIovecs`，再调用 `io_uring_register_buffers()` 注册给内核。连接读操作可以从 `freeBufferIndices_` 取一个索引，并使用 `io_uring_prep_read_fixed()`。

固定缓冲区的优点是内核不必为每个请求重复建立用户页映射，适合大量相同大小的小包；代价是启动时要锁定大量内存，并且每个 EventLoop 都有一份池。

当前默认估算值为：

```text
16384 个缓冲区 × 4096 字节 = 64 MiB / EventLoop
```

如果主循环加 16 个工作循环都初始化该池，仅数据页就可能达到约 1.06 GiB，还不包括 ring、连接、协程和其他内核结构。`io_uring_register_buffers failed: -12` 中的 `-12` 是 `-ENOMEM`，常见原因是 `RLIMIT_MEMLOCK` 或系统可锁定内存不足，而不是端口或 FD 上限。

### 9.2 linked timeout

读请求可以和超时请求组成 linked SQE：

```text
READ SQE --IOSQE_IO_LINK--> TIMEOUT SQE
```

读成功时，超时请求通常被取消并产生 `-ECANCELED`；读一直没有完成时，超时 CQE 会返回 `-ETIME`，连接随后执行关闭逻辑。调试时不要把所有负 errno 都当成系统故障：

- `-ECANCELED`：链中的超时被前一个 I/O 完成而取消，通常是正常路径。
- `-ETIME`：达到配置的超时时间，说明连接空闲或对端发送过慢。
- `-EPIPE`、`-ECONNRESET`：对端关闭或重置连接。

链式请求会带来额外 CQE，处理代码必须确保每一个 CQE 都有对应上下文，并且连接关闭后仍能安全处理迟到结果。

## 10. 异步写和发送路径

### 10.1 普通输出缓冲区

`asyncSend()` 先把数据追加到 `outputBuffer_`，再返回 `asyncWrite()`。写操作从可读区取数据，提交 socket 写请求；如果只写出一部分，必须更新读索引并继续提交，直到缓冲区清空。

这种路径适合 HTTP 响应、协议编码结果等需要在发送前拼接或暂存的数据。

### 10.2 固定缓冲区直写

`asyncSendRegisteredBuffer()` 直接发送当前读注册缓冲区，避免把数据再次复制到 `outputBuffer_`。它适合 Echo 或“读取后原样转发”的场景，但发送完成前不能归还该注册缓冲区索引。

### 10.3 sendfile 和 SEND_ZC

`AsyncWriteAwaitable` 提供几种特殊构造方式：

- `sendfile`：从文件 fd 直接发送到 socket，减少用户态文件缓冲复制。
- `IORING_OP_SEND_ZC`：尝试使用 io_uring 的零拷贝发送。
- 注册缓冲区版本：从已注册页发送，并在完成后归还索引。

这些接口是能力入口，不代表默认测试一定使用。默认 **`src/test.cpp`** 的 HTTP 测试主要走普通响应缓冲区；是否走零拷贝要以调用点和运行内核版本为准。

### 10.4 部分写

TCP 写操作可能只完成部分字节。正确实现需要保存未发送区间，处理 `res > 0`、`res == 0` 和负错误码，并在必要时继续提交。不能假设一次 `write` 就能发送完整响应，尤其是大响应或接收端较慢时。

## 11. Buffer 与协议解析

`Buffer` 把一段连续内存划分为：

```text
| 已读区域 | 可读区域 | 可写区域 |
           ^          ^
       readIndex   writeIndex
```

读入数据后推进 `writeIndex`；解析成功后推进 `readIndex`；当空间不足时移动或扩容。TCP 没有消息边界，因此一次 read 可能得到半个 HTTP 请求，也可能得到多个请求：

- 半包：保留已读数据，下一次 read 继续拼接。
- 粘包：循环解析，直到可读区不足以组成完整消息。
- 协议错误：记录错误并进入关闭流程。

当前默认测试程序包含一个简单 HTTP 处理路径；项目中还存在 codec 模块，但是否被默认入口使用，必须查看 **`src/test.cpp`** 的实际组装方式，不能仅凭目录名称判断。

## 12. 跨线程任务和 eventfd

当主线程需要让工作线程创建连接，或者工作线程需要请求主线程移除连接时，框架使用：

```text
生产线程 queueInLoop(functor)
      |
      +--> pendingFunctors_ 无锁队列
      +--> write(eventfd, 1) 唤醒目标 EventLoop
      |
目标 EventLoop 收到 eventfd CQE
      +--> 重新提交 eventfd 读
      +--> doPendingFunctors()
```

`runInLoop()` 如果发现调用者已经是目标线程，就直接执行回调；否则转为 `queueInLoop()`。这一判断避免了同线程场景不必要的队列和系统调用。

### 12.1 队列背压

`pendingFunctors_` 有容量、高水位和低水位：

- 入队失败时记录队列满次数并丢弃任务。
- 达到高水位时触发 `BackpressureCallback(true)`。
- 队列降到低水位时触发 `BackpressureCallback(false)`。
- `doPendingFunctors()` 批量取出任务，减少频繁竞争。

业务层可以在高水位时暂停接收新连接、限制任务生产或降低日志量。队列满时当前实现会丢弃投递任务，调用方必须评估这是否会影响连接生命周期和业务一致性。

## 13. 连接背压

连接级别的 `BackpressureStrategy` 定义了输出缓冲区达到高水位时的行为：

| 策略 | 行为 | 适用场景 |
| --- | --- | --- |
| `kDiscard` | 丢弃新数据 | 允许丢包的实时数据 |
| `kCloseConnection` | 关闭慢连接 | 强保护内存 |
| `kBlock` | 挂起发送协程，等待低水位 | 需要可靠发送 |
| `kPass` | 继续追加 | 业务自行保证上限 |

背压的目标不是让单个请求更快，而是避免慢客户端使服务端输出缓冲区无限增长。压测时应同时观察连接数、输出缓冲区、队列水位和内存。

## 14. 关闭、取消和异常路径

异步网络代码最容易出问题的地方是正常路径之外的生命周期：

1. 对端发送 FIN，读完成返回 0。
2. 对端发送 RST，读写可能返回 `-ECONNRESET`。
3. 读超时返回 `-ETIME`，链式请求的另一 CQE 可能返回 `-ECANCELED`。
4. 服务退出时，未完成请求可能被取消。
5. 连接对象已从主表删除，但旧 CQE 仍在 CQ 中。

检查实现时，重点确认每个分支是否做到：

- 不再提交新的无效 I/O。
- 不重复关闭 fd。
- 不重复归还注册缓冲区索引。
- 不在连接析构后恢复访问其协程或上下文。
- 不把正常取消误记成故障。

## 15. 配置与资源预算

配置文件的具体字段以当前 `config/ucp.conf` 为准。理解配置时可按四类归纳：

### 15.1 线程

线程数决定工作 EventLoop 数量。每增加一个 EventLoop，通常也会增加一个 ring、eventfd、任务队列和注册缓冲区池。

### 15.2 ring

`ringEntries` 决定 SQ/CQ 的容量。过小会导致 SQE 获取失败或提交压力；过大则增加内核映射和内存占用。它不是并发连接数，不能简单按连接数一比一设置。

### 15.3 注册缓冲区

总锁定内存近似为：

```text
EventLoop 数量 × registeredBuffersCount × registeredBuffersSize
```

例如 17 个 EventLoop、16384 个 4 KiB 缓冲区，约为 1.06 GiB。实际还要计入页对齐、ring、内核元数据和应用内存。出现 `-ENOMEM` 时，应先按该公式降低配置或提高 memlock，再判断是否需要更大的池。

### 15.4 队列

`pendingQueueCapacity` 只约束跨线程任务队列，不约束 TCP 输出缓冲区，也不约束系统 backlog。三者需要分别监控。

### 16.4 持续压测

另开终端运行一分钟压测，便于同时观察 CPU 和 I/O：

## 17. 性能观察方法

先找到真实服务端 PID，避免把 `sudo sh -c` 的包装进程当成目标：

```bash
pgrep -af proactor_test
SERVER_PID=$(pgrep -xo proactor_test)
echo "$SERVER_PID"
```

观察进程和线程 CPU：

```bash
top -H -p "$SERVER_PID"
pidstat -u -t -p "$SERVER_PID" 1
```

观察整机各 CPU 的用户态、内核态、软中断和 I/O 等待：

```bash
mpstat -P ALL 1
vmstat 1
iostat -xz 1
```

本机 loopback HTTP 压测通常不是磁盘 I/O；如果 `%iowait` 很高，应结合 `pidstat -d`、`iostat` 和 WSL/虚拟机环境判断，不能仅凭一个颜色或一行 `top` 输出认定服务端在等待磁盘。

常见指标解释：

- `wrk Requests/sec`：压测期间每秒完成的 HTTP 请求数（RPS）。
- `Transfer/sec`：每秒从服务端收到的响应字节数，受响应大小和 RPS 共同影响。
- 进程 `%CPU`：Linux 中通常按单个逻辑 CPU 为 100%，因此多线程进程出现 `500%` 表示约占用 5 个逻辑 CPU。
- `mpstat` 的 `%sys`：内核态 CPU 时间，网络系统调用和软中断会体现其中。
- `%iowait`：CPU 空闲但等待块设备 I/O 的时间，不能直接等同于网络等待。

## 18. 推荐源码阅读顺序

建议按“先静态结构，再动态请求”的顺序阅读：

1. **`src/test.cpp`**：确认服务器如何组装、回调如何写业务。
2. `TcpServer.hpp/cpp`：掌握启动、连接表和分发关系。
3. `Acceptor.hpp/cpp`：理解 accept 请求和连接风暴优化。
4. `EventLoop.hpp/cpp`：逐行跟踪初始化、主循环、CQE 分发和 eventfd。
5. `TcpConnection.hpp/cpp`：重点阅读状态、读写上下文和关闭路径。
6. `AsyncRead.hpp/cpp`、`AsyncWrite.hpp/cpp`：把 awaitable 的三个接口和 SQE 准备过程对应起来。
7. `IoContext.hpp`、`CoroutineTask.hpp`：理解 user_data、协程帧和结果传递。
8. `Buffer.hpp/cpp`：验证半包、粘包和部分写的处理。
9. `LockFreeQueue.hpp`、`MemoryPool.hpp`：最后再研究优化组件的内存序和回收策略。

每读完一层，都建议画出“谁拥有对象、谁提交请求、谁处理 CQE、谁负责释放”的四列表格。异步框架的正确性很大程度上取决于这四个问题是否始终有明确答案。

## 19. 建议重点审查的实现风险

以下不是对当前实现的定性结论，而是深入学习和后续生产化时应优先验证的点：

1. 注册缓冲区失败后的降级行为：日志记录 `-ENOMEM` 后，后续是否仍按 fixed buffer 路径提交，需要通过代码和运行日志确认。
2. linked timeout 的多 CQE 处理：读完成、超时取消和连接关闭之间是否可能重复恢复或重复清理。
3. 部分读写：业务协议是否假设一次读到完整请求，输出缓冲区是否正确处理短写。
4. `queueInLoop()` 满队列时丢弃任务：被丢弃的任务是否可能是连接销毁或必须执行的控制任务。
5. 高频日志：压测中同步日志可能显著提高 `%sys`、锁竞争和延迟，需区分框架开销与日志开销。
6. 零拷贝接口：`sendfile`、`SEND_ZC` 受内核版本、socket 类型和 buffer 生命周期约束，不能只以函数存在判断已生效。
7. 线程亲和性：线程池默认轮询分配，不等于固定 CPU 亲和性；需要单独用 `taskset` 或 `sched_setaffinity` 验证。
8. 同机压测偏差：客户端 `wrk` 与服务端竞争同一组 CPU，独立压测机的 RPS 和延迟可能明显不同。

## 20. 学习自测题

读完核心代码后，建议不看答案回答：

1. 为什么 `Acceptor` 只提交一个 io_uring accept，却能在一次回调中接收多个连接？
2. `IoContext::result_` 为什么不能直接从 CQE 指针长期保存？
3. `-ECANCELED` 在 linked timeout 中什么时候是正常现象？
4. 为什么每个 EventLoop 都有独立注册缓冲区会迅速放大 memlock 需求？
5. `runInLoop()` 和 `queueInLoop()` 如何避免同线程不必要的 eventfd 唤醒？
6. 一个 HTTP 请求被拆成三次 read 时，哪一层负责保存前两次数据？
7. 连接从 `connections_` 删除后，为什么还要回原 EventLoop 执行 `connectDestroyed()`？
8. 服务端进程显示 `500% CPU` 时，如何判断是服务端瓶颈还是同机 `wrk` 竞争造成的？

如果这些问题都能结合源码指出具体函数和对象，就已经掌握了本项目的主要运行骨架；之后再深入 codec、recommend 和压测脚本，会更容易判断哪些代码真正位于默认请求路径上。
